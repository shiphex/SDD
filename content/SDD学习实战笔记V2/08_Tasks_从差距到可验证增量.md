# 08 Tasks：从差距到可验证增量

## 1. 本文回答的核心问题

`08` 回答：怎样把 `01–07` 的目标设计与当前实现之间的差距，变成一个个可执行、可验证、可评审和可回退的增量。

Task 不是从架构目录或待办灵感中生成，而是从 Gap（差距）中推导。

## 2. 为什么需要这份文档

规格说明目标状态，却不自动告诉实现者从当前代码先走哪一步。没有滚动 Task 运营，常见问题是：

- 一个 Task 同时实现多个独立结果。
- 只列文件改动，没有可观察 Goal。
- 设计与现状冲突时，代码悄悄改变架构。
- 未来 Phase 的能力被顺手提前实现。
- 测试在编码后才决定，无法控制范围。
- 已完成任务持续被改写，历史证据丢失。

`08` 维护“现在从哪里出发、下一步改变什么、用什么证据结束”。

## 3. 写作前需要哪些输入

- `01–07` 中已接受且与当前增量相关的目标、边界、契约、失败、决定和验证。
- 指定代码或系统版本的当前事实。
- 工作区、依赖、测试和环境基线。
- 当前授权范围。
- 已完成任务的结果与尚未满足的目标。

如果关键事实未知，先创建 Investigation Task（调查型任务），不要用猜测编写 Implementation Task（实现型任务）。

## 4. 设计时应依次思考哪些问题

### 4.1 使用五段推导链

```text
Current State
  → Target
  → Gap
  → Smallest Delta
  → Evidence
```

- **Current State**：当前版本实际具有什么行为和约束。
- **Target**：`01–07` 已接受的近期目标状态。
- **Gap**：两者之间缺少的能力、规则或证据。
- **Smallest Delta**：能独立产生一个有价值结果的最小变化。
- **Evidence**：能够证明差距确实缩小的实际检查。

跳过 Current State 会得到空想计划；跳过 Evidence 会得到无法收口的实现。

### 4.2 维护 Current Facts

Current Facts 应：

- 只记录与近期 Task 直接相关的事实。
- 绑定到版本、路径、测试或观察证据。
- 与候选方案、Accepted Design Constraints 分开。
- 在每个 Task 完成后按影响范围刷新。

`01` 的设计基线解释“为什么有这个问题”；`08` 的 Current Facts 解释“当前 Task 为什么现在可以这样做”。

### 4.3 分开 Accepted Design Constraints

Accepted Design Constraints 汇总当前 Task 必须遵守的已接受规则，并指向 `01–07` 的主要定义位置。它不是新的权威来源。

不要把 Proposed 或 Deferred 内容混入约束表。只有经过规定评审并接受的决定才能约束实施。

### 4.4 从能力成熟度推导 Phase

Phase 是一组有顺序依赖的能力阶段。推荐按“先建立可验证基础，再扩展行为”排序，而不是按目录或团队分工排序。

例如：

1. 核实当前路径和测试基线。
2. 建立最小领域状态与契约。
3. 接入一个端到端主链。
4. 补充失败恢复与兼容迁移。
5. 扩展规模或自动化。

Phase 可以在新证据出现后重排。未来阶段只保留方向和重审条件。

### 4.5 使用纵向切片

Vertical slice（纵向切片）贯穿完成一个可观察结果所需的最少层级，而不是一次实现某一层的所有代码。

一个好的 Task 通常满足：

- 只有一个主要结果。
- 结果可独立验证。
- 失败边界清楚。
- 修改范围可审阅。
- 不依赖尚未裁决的关键决定。
- 完成后系统处于可用且一致的状态。

如果标题中需要多个“以及”，优先检查是否应拆分。

### 4.6 编写 Task 的控制字段

近期 Task 至少包含：

- **Goal**：结果式目标。
- **References**：具体 Spec 条目，不是只列文件名。
- **Preconditions**：为什么现在可以开始。
- **Allowed scope**：允许修改的职责区域，必要接缝如何处理。
- **Must**：完成 Goal 必需的最小事实。
- **Must not**：最可能出现的范围扩张或边界破坏。
- **Verify**：编码前定义的证据。
- **Design Delta rule**：何时停止并回到设计。

控制项应从风险生长。例如编排层可能变成上帝对象，就在 Must not 中禁止吸收领域规则，并在 Verify 中增加边界检查。

### 4.7 区分调查型和实现型任务

| 类型 | 主要输出 | 完成含义 |
| --- | --- | --- |
| Investigation Task | 可核查事实、差距、选项、风险与建议 | 证据足以支持裁决或后续 Task |
| Implementation Task | 行为增量、实际验证和完成记录 | Goal 达成且所有完成条件满足 |

调查报告不是能力增量，不能因为“报告写完”就勾选功能 Phase。实现任务也不应被要求产出大而泛的研究报告。

### 4.8 为高风险任务设置 Preflight

Preflight（实施前检查）推荐包含：

1. Baseline：版本、工作区和基线检查。
2. Confirmed Implementation Facts：动手前核实的实现事实。
3. Planned Modules：计划修改的职责区域与最小接缝。
4. Design Deltas Requiring Review：Spec 无法唯一确定的高影响问题。
5. Verification Gate：进入实施必须满足的门槛。

结论使用 `Ready` 或 `Blocked`。低风险、容易回退的局部任务可以缩短或省略独立 Preflight。

### 4.9 编写 Completion Report

Completion Report（完成报告）至少包含：

1. Implemented：实际实现的结果。
2. Files Changed：修改范围及原因。
3. Tests：实际运行的检查、结果和基线。
4. Boundary Checks：Must not、禁止依赖和零修改区域。
5. Design Deltas：实现中发现并处理或未处理的变化。
6. Remaining Risks：仍存在但不阻塞当前完成的风险。
7. Outcome：Done / Blocked / Partial。

项目明确要求 Completion Review 时，报告未经接受前，Task 保持 `In Review`，不直接标记 Done。

### 4.10 定义 Done

Task 只有同时满足以下条件才是 Done：

1. Goal achieved：主要结果已实现。
2. Verify passed：必需验证具有当前基线的实际证据。
3. Must not respected：范围和架构禁止项未被违反。
4. No unresolved Design Delta：当前范围没有未解决的设计变化。
5. Required review accepted：项目规定的评审已经完成。

测试文件存在、局部测试通过或实现代码完成，都只证明各自范围。

### 4.11 滚动维护过去、现在和未来

- **过去压缩**：完成的 Task 进入一行摘要，详细证据保留在版本历史或里程碑归档。
- **现在详细**：当前 Task 保留完整控制字段、状态和阻塞信息。
- **未来粗略**：远期 Task 只写方向、依赖和重审条件。

这就是 Rolling-Wave Planning（滚动式规划）：越近越具体，越远越允许被新证据修正。

### 4.12 保留历史但不让历史定义当前事实

只归档能够解释重大变化、且当前 Spec / ADR 无法完整表达调查过程的 milestone evidence（里程碑证据）。普通测试输出、临时 brainstorm 和失败的提示词输出不需要长期入档。

三类信息各归其位：

- 当前系统事实与当前计划 → `08`。
- 已接受的长期设计规则 → `01–07` 对应位置。
- 当时发生过什么 → 版本历史与必要归档。

## 5. 最小内容与高风险扩展内容

### 5.1 最小内容

- Current Facts
- Accepted Design Constraints 引用
- 当前 Phase 与 Goal
- 一个近期 Task 的 Goal、范围、Must / Must not、Verify
- 状态与完成记录

### 5.2 高风险扩展

- Gap Analysis
- Preflight 和人审门槛
- 详细基线与证据引用
- Design Delta 日志
- Completion Report
- 历史归档入口
- Phase 重排与重审原因

## 6. 独立虚构示例

> 教学推演：以下“社区菜谱索引器”完全虚构，只用于说明 Task 推导。文件、状态和检查均为示例，不代表实际运行。

### 6.1 Current State

- 当前命令每次只读取一个菜谱文本。
- 解析结果只输出到终端，没有稳定的领域结果对象。
- 已有单文件格式错误测试。

### 6.2 Target

一次导入可以接收一个目录，并返回每个文件的成功或失败结果；单个文件失败不阻止其他文件处理。

### 6.3 Gap

- 缺少可复用的单文件结果类型。
- 缺少批次级编排入口。
- 现有失败以异常中断整个命令。

### 6.4 Phase

- Phase 1：建立单文件稳定结果，不改变命令行入口。
- Phase 2：增加批次编排和部分失败。
- Phase 3：接入目录入口并验证兼容。

### 6.5 TASK-01：建立单文件解析结果契约

**Goal**：调用解析用例后，可以得到明确的成功结果或格式失败结果，既有单文件命令行为保持不变。

**References**：`CONTRACT-PARSE-01`、`F-PARSE-01`、`TEST-CONTRACT-01`（均为本虚构案例中的假定编号）。

**Preconditions**：单文件入口和基线测试已核实；结果类型的领域失败语义已经接受。

**Allowed scope**：解析用例、结果类型、对应定向测试；命令入口只允许最小适配。

**Must**：

- 成功结果携带规范化标题。
- 格式失败使用稳定领域结果。
- 旧命令的成功与错误退出语义保持兼容。

**Must not**：

- 不扫描目录。
- 不实现批次循环。
- 不引入并发或缓存。

**Verify（Planned）**：

- 契约测试覆盖成功和格式失败。
- 执行既有单文件命令回归测试，预期保持通过。
- 变更检查确认没有目录扫描能力。

**Design Delta rule**：若现有命令依赖原始异常类型作为公开行为，停止实施并回到 `04/06` 裁决兼容策略。

这个 Task 之所以先于批次入口，是因为它先建立可组合、可验证的最小结果语义。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| 从文件列表生成 Task | 完成后谁能观察到什么新结果？ | 从 Gap 写结果式 Goal |
| 一个 Task 包含多个独立结果 | 任一部分失败时其余部分能独立完成吗？ | 拆成纵向切片 |
| References 只写文件名 | 具体受哪条规则约束？ | 引用条目或编号 |
| Allowed scope 预测所有文件 | 真正允许改变的是哪些职责？ | 用职责区域加最小接缝 |
| Verify 在编码后补 | 什么证据能阻止错误方向？ | 动手前写验证 |
| 实现困难就改 Spec | 是设计不成立还是局部实现选择？ | 先分类 Design Delta |
| Done Task 被反复改写 | 当时的 A→B 变化还可追溯吗？ | 压缩摘要，保留历史 |

## 8. 与其他文档的输入、输出和更新关系

- 从 `01–07` 接收当前 Task 的设计依据，不复制其完整定义。
- 向实施提供近期目标、范围、禁止项和验证门槛。
- 实现发现 Design Delta 时，按冲突层级回到 `01–07`。
- Task 完成后刷新受影响的 Current Facts、规范传播状态和验证状态。
- Human Review 的门槛与裁决方式见 `09`。

## 9. 什么变化会触发本文更新

- 当前实现或基线证据改变。
- 已接受的目标、设计约束或验证方式改变。
- 当前 Task 完成、阻塞、拆分或重新排序。
- 新证据暴露依赖、范围或 Phase 假设错误。
- Design Delta 被接受、拒绝或延期。

只更新受影响的当前与未来计划，不用新事实改写已完成任务的历史含义。
