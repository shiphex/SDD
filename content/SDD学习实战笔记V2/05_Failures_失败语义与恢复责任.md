# 05 Failures：失败语义与恢复责任

## 1. 本文回答的核心问题

`05` 回答：哪里可能失败，谁发现，怎样传播，谁负责恢复，是否允许重试、回滚或清理，以及最终留下什么可观察状态。

错误处理首先是设计问题。`try/catch` 或 `try/except` 只是实现机制，不能替代失败责任和结果语义。

## 2. 为什么需要这份文档

成功路径通常只有一条，失败路径却可能改变状态、资源和外部世界。如果没有统一设计，常见结果是：

- 底层静默吞掉错误，上层误以为成功。
- 多层同时重试，造成放大流量或重复副作用。
- 构造一半失败后泄漏资源。
- 清理失败覆盖最初的业务错误。
- 响应丢失后盲目重试一个可能已成功的外部动作。
- 失败记录被删除，调用方无法查询最终状态。

`05` 让失败成为可以编号、追踪和验证的规格。

## 3. 写作前需要哪些输入

- `01` 的失败相关成功标准和质量驱动。
- `02` 的状态、资源与生命周期 owner。
- `03` 的主链、失败分支、提交点和终态。
- `04` 的领域失败、超时、取消和幂等语义。
- 外部依赖能够保证和不能保证的行为。

不要根据库名称猜测失败语义。需要时先查当前实现或官方契约，并标明适用版本。

## 4. 设计时应依次思考哪些问题

### 4.1 建立全局 Failure Policy

Failure Policy（失败策略）是一组跨场景默认规则。推荐至少裁决：

- 预期领域失败是否使用稳定类型或结果表示。
- 哪一层可以重试，其他层是否禁止重复重试。
- 部分构造失败如何回滚已获得的所有权。
- `shutdown` / `close` 是否要求幂等。
- 多项清理如何 best-effort（尽力执行）并汇总错误。
- 原始失败与清理失败如何同时保留。
- 非法状态转移如何响应。
- 外部结果未知如何表示和恢复。

Policy 是推荐默认与项目决定的结合，不是通用真理。与现状或 Driver 冲突时应通过 ADR 裁决。

### 4.2 分类错误

| 类别 | 含义 | 常见处理方向 |
| --- | --- | --- |
| Programmer error | 实现或调用违反内部不变量 | 快速暴露、修复代码 |
| Domain failure | 业务条件不允许当前操作 | 返回稳定领域结果 |
| Environment failure | 文件、网络、权限等环境问题 | 传播、降级或恢复 |
| Transient failure | 可能短暂消失的失败 | 有边界地重试 |
| Permanent failure | 在当前输入和条件下不会自行恢复 | 停止重试并报告 |
| Cancellation | 调用方请求停止后续工作 | 清理可取消部分，保留已提交事实 |
| Timeout | 等待超出时限 | 区分确定失败与结果未知 |

分类的目的不是给异常贴标签，而是决定恢复动作和调用方可见语义。

### 4.3 为每个关键失败回答八问

1. 在哪里发现？
2. 怎样传播给谁？
3. 谁是 recovery owner（恢复责任方）？
4. 是否可重试，重试预算和退避是什么？
5. 重试是否依赖幂等？
6. 需要回滚、补偿或清理什么？
7. 最终状态是什么，是否可查询？
8. 需要产生什么事件或证据？

将答案写成带编号的 Failure 条目，供 `07/08` 引用。

### 4.4 区分回滚、补偿和清理

- **Rollback（回滚）**：在同一所有权边界内撤销尚未提交的局部变化。
- **Compensation（补偿）**：外部或已提交动作无法真正撤销时，执行一个新的修正动作。
- **Cleanup（清理）**：释放资源或结束生命周期，不一定改变业务结果。

三者语义不同。把补偿写成回滚会让人误以为外部世界恢复到从未发生过的状态。

### 4.5 设计部分构造失败

对象或资源按多个步骤创建时，任一步骤失败都要回答：

- 已成功获得了哪些资源？
- 临时 owner 是谁？
- 最终 owner 在什么时候接管？
- 清理失败怎样报告？

一种稳健的设计是：在全部构造成功前由局部构造过程持有资源，成功后一次性交给长期 owner。

### 4.6 控制重试

重试必须有：

- 明确的唯一责任层。
- 可识别的 transient 条件。
- 次数、时限或总体预算。
- 幂等或去重依据。
- 最终放弃后的状态与观察方式。

多层重试会指数放大请求。没有接收端幂等或结果查询时，外部副作用通常不能仅因超时就自动重试。

### 4.7 处理响应丢失和结果未知

当请求可能已经到达外部系统，但响应没有返回：

- 不推断“没有发生”。
- 本地记录请求标识和未知状态。
- 若支持结果查询，按同一关联标识查询。
- 若支持接收端幂等，才在契约范围内重放。
- 若两者都不支持，升级给人工或业务补偿流程。

“未知”是诚实且可操作的状态，不是实现失败。

### 4.8 防止级联失败

检查：

- 一个组件失败会不会触发所有上游同时重试？
- 清理一个资源失败会不会阻止其他资源清理？
- 非关键依赖失败是否需要让主流程整体失败？
- 是否需要隔离、限流、熔断或降级？

具体机制只有在风险和证据支持时才决定，不要看到“分布式”就自动引入新基础设施。

## 5. 最小内容与高风险扩展内容

### 5.1 最小内容

- Failure Policy
- 错误分类
- 带 ID 的关键失败表
- 每个失败的检测、传播、恢复 owner 和最终状态
- `07/08` 的验证入口

### 5.2 高风险扩展

- 重试预算和退避
- 幂等与结果查询
- 补偿流程
- 部分构造和重复关闭
- 多项清理与错误聚合
- 级联失败、隔离与降级
- 人工恢复或对账路径

## 6. 独立虚构示例

> 教学推演：以下“天文观测预约导出器”完全虚构，只用于说明失败语义；没有真实外部服务或测试结果。

系统将已批准的预约导出给外部排程服务。

### 6.1 Failure Policy 摘要

- 只有 Export Coordinator 可以重试外部导出。
- 每次导出使用稳定的 `export_request_id`。
- 外部响应丢失后，状态进入“导出结果未知”，不自动创建新请求标识。
- 清理临时文件失败不得覆盖原始导出错误，两者都要记录。

### 6.2 Failure 表

| ID | Failure | Detect | Recovery owner | Action | Final state / Evidence |
| --- | --- | --- | --- | --- | --- |
| F-EXP-01 | 预约已撤销 | 导出前校验 | Reservation Book | 拒绝导出 | 保持“已撤销” |
| F-EXP-02 | 外部服务明确拒绝 | 响应校验 | Export Coordinator | 不重试，保存拒绝原因 | “导出失败”可查询 |
| F-EXP-03 | 请求发送后响应丢失 | 等待超时 | Export Coordinator | 使用原标识查询；无查询能力则转人工 | “导出结果未知” |
| F-EXP-04 | 临时文件删除失败 | cleanup | Export Coordinator | 继续其他清理并汇总 | 业务结果不被覆盖 |

### 6.3 关键判断

`F-EXP-03` 不能写成“导出失败并重试”。请求可能已经生效；只有外部服务的幂等和查询契约能够决定是否安全重放。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| 所有错误都重试 | 哪些失败会自行恢复？ | 分类并设置唯一重试层 |
| 回滚与补偿混用 | 外部动作真的能被撤销吗？ | 分开撤销与新修正动作 |
| 清理遇错即停 | 后续资源是否因此泄漏？ | best-effort 并聚合错误 |
| 超时后重新生成请求 | 原请求可能已成功吗？ | 保留标识和未知状态 |
| Failure 没有 owner | 最后谁负责把状态收敛？ | 指定恢复责任方 |
| 只写日志不定义结果 | 调用方能查询什么终态？ | 明确可观察最终状态 |

## 8. 与其他文档的输入、输出和更新关系

- 从 `02` 接收资源、状态和生命周期 owner。
- 从 `03` 接收失败发生位置、提交点和终态。
- 与 `04` 对齐领域失败、超时、取消、幂等和未知结果。
- 输出给 `07`：每个 Failure ID 的验证场景。
- 输出给 `08`：必须实现和检查的恢复行为。
- 影响范围较大的策略取舍记录到 `06`。

## 9. 什么变化会触发本文更新

- 新增失败类别、检测点或恢复路径。
- 恢复 owner、重试责任层或预算改变。
- 幂等、超时、取消或结果未知语义改变。
- 回滚、补偿、清理和终态保留方式改变。
- 外部依赖的实际保证发生变化。

仅修改错误文本且不影响调用方语义时，通常不更新 `05`。
