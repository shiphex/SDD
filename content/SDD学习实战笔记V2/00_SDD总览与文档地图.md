# SDD 总览与文档地图

> 本知识库整理的是一套个人实践版的 Spec-Driven Development（规格驱动开发，简称 SDD）方法。它用于帮助开发者在 AI 参与的软件开发中明确问题、约束设计、拆分任务并用证据验收，不代表统一的行业标准。

## 1. 本文回答的核心问题

这份入口页回答三个问题：

1. SDD 要解决什么问题？
2. 七步工作流与 `01–08` 八类设计信息是什么关系？
3. 面对不同任务，应从哪篇笔记开始读？

## 2. 为什么需要 SDD

让人或 AI 从一句意图直接进入编码，常见风险不是“代码一定写错”，而是中间判断没有被看见：

- 当前实现和限制没有核实，旧文档或猜测被当成事实。
- 目标、方案和文件改动混在一起，局部实现反过来定义需求。
- 状态、所有权、失败恢复和兼容语义没有明确归属。
- 一次任务包含多个结果，修改范围和停止条件持续扩张。
- 测试计划、脚本退出码或文件存在被误当成完整的完成证据。

SDD 在意的不是“先写很多文档”，而是把决定实现方向的信息显式化，并让它们能够被检查、修正和追溯。

## 3. 总体模型

本知识库使用下面的总体模型：

```text
Intent
  → Specification
  → Design
  → Verification
  → Implementation
  → Feedback
```

- **Intent（意图）**：为什么要改变，谁会受到影响。
- **Specification（规格）**：预期结果、范围、约束和成功标准。
- **Design（设计）**：边界、运行流程、契约、失败语义和取舍。
- **Verification（验证设计）**：需要什么证据才能接受结果。
- **Implementation（实施）**：把现状与目标之间的差距变成小步增量。
- **Feedback（反馈）**：实现和评审产生新证据后，回到真正需要修正的层级。

这条链不是瀑布式单行道。后面的证据可以推翻前面的假设，但变化应先回到正确的权威位置，再传播到受影响的下游内容。

## 4. 两个视角：七步活动与八类信息

### 4.1 七步工作流回答“活动怎样推进”

权威操作流程见[七步 SDD 工作流](../../skills/sdd/references/workflow.md)：

1. 明确目标与验收。
2. 核实当前状态。
3. 设计必要边界。
4. 确定关键决定。
5. 推导最小可验证增量。
6. 实施并处理变化。
7. 验证并同步。

步骤可以回退，也不要求每一步都新建一份文件。

### 4.2 `01–08` 回答“需要维护哪些信息”

| 文件 | 主要职责 | 典型输出 |
| --- | --- | --- |
| [01 Problem](01_Problem_问题目标与成功标准.md) | 定义问题、目标与成功标准 | Goal、Non-goal、SC |
| [02 Architecture](02_Architecture_边界职责与所有权.md) | 定义静态边界、职责与所有权 | 构件、May / Must not、不变量 |
| [03 Runtime](03_Runtime_运行流程状态与生命周期.md) | 定义运行流程、状态和生命周期 | 主链、失败分支、状态机 |
| [04 Contracts](04_Contracts_模块交互规则.md) | 定义模块间可以依赖的交互规则 | 操作、前后置条件、状态效果 |
| [05 Failures](05_Failures_失败语义与恢复责任.md) | 定义失败分类、传播和恢复责任 | Failure Policy、Failure ID |
| [06 Decisions](06_Decisions_设计取舍与决策记录.md) | 记录关键取舍及其理由 | ADR、风险、重审条件 |
| [07 Test Plan](07_Test_Plan_验证设计与完成条件.md) | 设计需求、契约和架构的证明方式 | 测试分层、QAS、追踪矩阵 |
| [08 Tasks](08_Tasks_从差距到可验证增量.md) | 从现状与目标的差距推导增量 | Current Facts、Task、完成记录 |

`06` 的编号是文件位置，不是“到第六步才做决定”。重要取舍可能在目标澄清、边界设计、实现调查或失败分析时出现，统一记录到 `06`，再影响其他文档。

### 4.3 两者的映射

| 七步活动 | 主要读取或更新的文档 | 说明 |
| --- | --- | --- |
| 1. 明确目标与验收 | `01`，初步 `07` | 先定义结果和所需证据 |
| 2. 核实当前状态 | `01` 的设计基线、`08` 的 Current Facts | 前者解释问题背景，后者随实施滚动刷新 |
| 3. 设计必要边界 | `02–05`，初步 `07` | 按风险选择需要的视图 |
| 4. 确定关键决定 | `06`，并回写受影响的 `01–05/07` | 决定位置贯穿全程 |
| 5. 推导最小增量 | `08` | 从 Gap 推导近期 Task |
| 6. 实施并处理变化 | `08`，必要时回到 `01–07` | 新证据不应被代码悄悄吸收 |
| 7. 验证并同步 | `07/08`，以及实际受影响的规范 | 区分计划、执行结果与完成结论 |

步骤编号与文件编号不是一一对应关系。工作流是一组活动，文档是一组信息容器。

## 5. 两大支柱与反馈方向

```text
支柱 A：Spec 编写（01–07）          支柱 B：Spec 执行（08）
┌──────────────────────────┐       ┌────────────────────┐
│ 目标 → 边界 → 流程 → 契约 │  ───→ │ 当前事实 → Gap → Task│
│      → 失败 → 决策 → 验证 │       │       → 实现 → 证据 │
└──────────────────────────┘       └─────────┬──────────┘
        ↑                                    │
        └──── Feedback / Design Delta ───────┘
```

- 支柱 A 决定“做什么、做到哪里、不得破坏什么、怎样证明”。
- 支柱 B 把这些约束与当前实现对照，形成可以执行和验收的增量。
- 实现证据推翻设计时，通过 Design Delta（设计变化请求）回到正确层级，而不是在任务里暗改规则。

完整的双反馈循环和 Human Review（人工评审）见[09 Feedback、Human Review 与思维内化](09_Feedback_Human_Review与思维内化.md)。

## 6. 文档深度随风险调整

以下是推荐默认，不是按文件数量考核的规定：

| 变化类型 | 建议记录方式 |
| --- | --- |
| 局部、容易回退、无公开契约变化 | 可在一份短 Spec 中合并实际相关的信息 |
| 跨模块、存在状态或失败路径 | 分开维护受影响的 `01–08` 文档 |
| 涉及公开契约、持久化、外部副作用或复杂生命周期 | 深入补齐 `03–07`，明确提交点和恢复责任 |
| 高影响或难回退决定 | 使用 ADR，并设置 Design Review |

即使物理上合并文件，也仍需覆盖真正相关的信息类别。反过来，没有内容的章节不应为了“齐全”而填充套话。

## 7. 四类规则标记

本知识库用以下词语避免把建议写成绝对要求：

- **工作流规定**：为了保持本方法内部一致性而必须遵守的规则。
- **推荐默认**：通常有效，但可以依据项目条件调整。
- **风险适配**：是否采用取决于可逆性、影响范围、外部副作用等风险。
- **教学推演**：用于解释方法的虚构例子，不代表实际系统已实现或验证。

## 8. 阅读路径

### 第一次学习

按 `00 → 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09` 阅读。先理解每类信息解决什么问题，再尝试模板。

### 开始设计一个功能

从[01](01_Problem_问题目标与成功标准.md)明确问题和成功标准，然后按风险阅读 `02–07`。不要从 Task 模板或文件清单开始。

### 拆分和维护 Task

直接阅读[08](08_Tasks_从差距到可验证增量.md)，并回看它引用的 `01–07`。Task 不是另一份需求文档，而是“现状到目标”的最小可验证变化。

### 审核报告或设计变化

先阅读[09](09_Feedback_Human_Review与思维内化.md)中的评审门槛，再根据冲突所在层级进入 `01–08`。可复制结构见[Human Review 模板](templates/Human_Review模板.md)。

### 为博客、文章或视频选材

从专题笔记抽取一个问题、一条推理链和一个虚构案例，再重新组织叙事。知识库已按公开安全要求编写，但发布前仍需复核来源、链接和平台表达。

## 10. 使用边界

- 历史聊天和旧笔记是内部参考，不直接定义当前方法。
- 当前事实必须由指定版本的代码、测试或观察支持。
- 设计预期必须标为预期；只有实际执行的检查才能写成验证结果。
- 外部动作在响应丢失后可能已经发生。没有接收端幂等或结果查询能力时，结果应保持“未知”。
- 内容制作可以使用虚构 Spec、伪代码和图示说明，但不能把教学推演写成真实验证。
