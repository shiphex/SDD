# 术语与方法索引

查阅日期：2026-09-14。

## 2. 外部方法与本知识库的关系

### GitHub Spec Kit

[GitHub Spec Kit](https://github.com/github/spec-kit) 是公开的 spec-driven 工具项目，强调先定义要构建的内容，再由任务和实现推进。它可以作为工具实践参考；本知识库的 `01–08` 信息结构和七步工作流是独立整理，不等同于 Spec Kit 的命令或版本流程。

### C4 model

[C4 model 的 diagram 指南](https://c4model.com/diagrams)提供按沟通目的选择软件系统、容器、组件等视图层级的方法。本知识库借用“先解释边界和主要构件，再决定是否需要更细视图”的思路，不要求每个项目维护固定数量的图。

### arc42

[arc42 模板总览](https://arc42.org/overview/)提供软件架构文档的结构化问题地图。这里把它当作检查覆盖面的参考，不要求按其章节逐项生成文档。

### Architecture Decision Records

Michael Nygard 的[《Documenting Architecture Decisions》](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)介绍了用 Status、Context、Decision 和 Consequences 保存架构决定的轻量记录方式。本知识库在此基础上增加 Verification、Escape Hatch、Review Trigger 和传播状态，以适配当前工作流。

### ATAM

Carnegie Mellon University Software Engineering Institute 的[ATAM 资料集](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)说明了以业务驱动和质量属性场景评估架构，并识别风险、敏感点和取舍点的方法。本知识库中的 “mini-ATAM” 是个人实践的轻量化借鉴，不代表执行了正式 ATAM 评估。

### Evolutionary architecture

[Thoughtworks 的《Building Evolutionary Architectures》页面](https://www.thoughtworks.com/insights/books/building-evolutionary-architectures)可用于继续了解演进式架构和 fitness function（适应度函数）思路。本知识库将可自动检查的依赖和边界规则视为架构验证的一部分，但不要求所有规则都自动化。

### 软件工程与评审

[Software Engineering at Google 在线版](https://abseil.io/resources/swe-book)可用于延伸阅读设计文档、评审、测试和长期维护。本知识库不把其中任一团队实践直接写成普遍规则。

### iSAQB 学习材料

[iSAQB Advanced Level 模块页](https://www.isaqb.org/certifications/cpsa-certifications/cpsa-advanced-level/)提供多个软件架构进阶主题入口，其中包括面向 Agentic Software Engineering Contexts 的 AGENTA。它适合作为系统学习线索，不是本工作流效果的证明。

## 3. 建议学习顺序

1. 用 C4 和 arc42 学会按沟通问题选择边界与视图。
2. 用 Runtime View、状态机和 Contract 练习描述跨模块行为。
3. 用 ADR 保存关键取舍，用 QAS 把质量目标变成场景。
4. 用 ATAM 的风险、敏感点和取舍点训练方案比较。
5. 用架构检查和小步 Task 观察设计能否在长期变化中保持。
6. 最后再选择 Spec Kit 或其他工具自动化适合自己的部分。
