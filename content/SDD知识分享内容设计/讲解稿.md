---
(背景介绍)

首先，第一个问题，什么是“规格驱动开发”呢？

规格驱动开发， SDD ，即 Spec-Driven Development。
就是在实际编写代码前，先构建一个足够明确、足够可验证的规格文档，
但这个文档不是越详细越好，否则给人制造大量文档维护成本。
然后通过该文档驱动后续代码编写、测试、迭代的软件开发方法论。

第二个问题，在 AI 时代，为什么需要规格驱动开发？

AI 时代下，代码的产生速度已经成百上千倍的提升了，
但在使用 AI Coding 编写代码时，只要系统变得复杂，
代码量变得庞大，AI Coding 生成的代码就会变得越来越发散，
可读性越来越差，比古法编程时代更快的变成一座屎山。
当然，Spec 自己也可能错，
所以需要把 Spec 当作可验证的假设模型，用现实和实现证据来检验它。

第三个问题，在 AI 时代，AI 显著降低了部分代码生成和执行工作的成本。

初级岗位的工作内容，
往往是听从领导，根据规格文档进行开发，比如，
“这个功能怎么实现？”，“接口怎么设计？”。
从更高纬度的视角来看，
能够问题定义、约束设计、判断、验证的能力重要性上升了。

为了能够更好的与 AI 合作进行设计开发，
并同时拥有更高维度的分析、设计、评估能力，
所以我决定学习并实践 SDD 规格驱动开发。

(问题)

那么，应该怎么做？这套文件体系又是怎么样的？

---
(回答)

践行 SDD 规格驱动开发的核心其实是在人的活动，
人要做的是：
1. 明确目标、Non-goal、Success Criteria
2. 核实 Current Reality 与约束
3. 设计职责、边界、行为、契约、失败语义
4. 裁决关键 Design Decisions
5. 定义 Verification Plan：怎样证明目标和关键风险被满足
6. Current Reality 与 Target Spec 求差，形成 Gap
7. 从 Gap 推导最小可验证 Task
8. Implementation → Evidence → Review → 更新 Reality / Spec

而文件系统只是信息地图。

我设计的这套文件体系由两个模块 "Spec 编写"和 "Spec 执行"，及一条反馈回路构成。
"Spec 编写"模块负责保存当前有效规格。
"Spec 执行"模块负责保存当前事实、Tasks。
反馈回路，负责 Feedback / Review / 变化路由。

第一个模块 "Spec 编写"，包含文件：
1 problem.md，用于描述问题，设计目标及成功标准。
2 architecture.md，用于描述系统、模块的架构设计，并规范模块命名。
3 runtime.md，用于描述系统、模块的运行时行为。
4 contracts.md，用于描述模块的接口及相互之间的交互设计。
5 failures.md，用于描述系统、模块的失败策略。
6 decisions.md，用于记录设计决策。
7 test-plan.md，用于描述测试计划。

第二个模块 "Spec 执行"，包含文件：
8 tasks.md，用于描述需要执行的任务，包括总体任务列表、子任务列表、阶段任务、任务详细描述等。
执行结果为 Agent 给出的带上提交哈希、测试日志、代码变动等原始信息的报告。

反馈回路：
9 review.md，用于记录出现问题或需要调整时，通过反馈回路对规格文档进行调整的内容。

这些文件并非按排序进行书写，比如，
你可能在 problem 阶段就做决策，
在 architecture 阶段做决策，
在实现过程中也会产生决策，
然后在产生决策时就应该编写到 06 decisions.md 中。

首先，第一个文件是 problem.md，
这个文件覆盖了 Intent 和 Specification 两个阶段，
首先需要描述背景，也就是需求是什么。
然后要明确当前状态，即系统现有代码的情况，
以及用户现状、运行环境、外部系统、组织约束等。
如果还没开始编码，可以分析一下当前要解决真正的问题是什么。
即“为什么这是问题、问题基线、必要事实、Assumption / Unknown”。

然后是制定设计目标，描述期望得到的可观察的产品结果。
如果希望通过开发学习经验，也可把学习目标等列举出来。
如果想先将最小系统实现，可添加描述阶段开发目标。

在制定完目标后，一定要编写 Non-goal，
填充最容易被 Agent 顺手扩张、但本次不做的内容，
避免 Agent 在编程时顺手实现非目标功能。

然后是编写成功条件，即描述做到什么程度，
我可以宣布这次开发成功，而不是继续“优化”。
相关描述可使用编号，SC-XX，
以便在后续的测试、验收、迭代中引用。
通过自然语言描述成功条件，若不知如何描述，
相关描述可选择使用 Given、When、Then 模板，
即：在什么初始条件下，触发什么操作后，
期望得到什么结果，从而清晰的表达。

最后是对质量属性的描述。
质量属性包括可修改性、可测试性、可靠性、延迟等等。
可以用“在什么刺激下，系统在什么环境里，以什么响应达到什么度量”让这些属性可以设计和验证。

另外，若有暂时无法明确的项目，
或者有会影响设计的情况，
可以在本文档的最后记录。

包括全局失败策略、具体失败策略等。

全局失败策略，具体描述：
定义异常的“语言”，AI 必须知道什么时候该用强类型的领域异常，什么时候向上抛。
指定“谁”才是唯一能发起重试的负责人。
防止“部分执行”污染，如果复合对象只构造了一半就报错，必须要有相应的处置措施。
确保系统退出、或者资源释放操作是安全的。
不能因为清理 A 失败了，就不去清理 B。
防止在非法状态下运行。
未知外部结果处理。

具体失败策略，用于记录详细的失败场景：
包括：编号、失败描述、描述何处失败的检测点、问题的接收方和责任方，
以及相应的处理规则和动作，失败处理的最终状态。
没有的条目可以取消该列。

最后，如果有必须处理的失败场景，
可在最后记录。

(拓展)

关于程序模块的设计，
我推荐使用《软件设计哲学》这本书中推荐的深模块设计。

这样不用为了众多小模块，单独设计架构、运行时、交互等，
在 AI coding 时，这样做就可以避免模块调用混乱的问题。

同时避免我们在做架构设计时出现“察察之明”的情况，
就比如《资治通鉴》中，魏文侯明乐音而不明乐官的故事，
但贤明的国君应该去考核、了解‘乐官’（主管音乐的官员）是否称职，
而不是去亲自钻研‘乐音’（具体的音准、乐理）。

同理，在设计架构时，如果使用深模块的设计模式，
用简单接口隐藏大量内部复杂性，
让通过更稳定、更小的跨模块知识面，
让 Contract 更简单，架构认知负担降低
而能更好的把精力放到对架构的设计上。

用简单接口隐藏大量内部复杂性。
在 SDD 时若无优化诉求，上层使用者不必深入模块内部细节；
但模块内部的高风险逻辑，仍需要基于风险做好设计。

我们先来看 decisions.md 文件。

该文件记录对架构、质量属性或长期演进产生明显影响的设计决策。

这些决策使用 ADR-xx 编号 + 描述的方式作为标题。

不能改变的性质，
驱使该决策的驱动因素，

然后可以列表给出不同的决策选项，

得到是否接受该决策。

并得出结论，这项选择获得什么，失去什么，
以及因为这项决策需要新增的内容。

如果决策依然无法得到定论，
则需要说明延迟的原因。

(描述)

"Spec 执行" 的核心文件是 tasks.md，
在这个文件中，
首先编写总体任务目标，
包括：MVP 最小可交付产品的描述，
以及一些可选目标描述，
另外，需要列举出任务的阶段计划。

然后，要列表说明当前事实以及已接受的设计约束，
当前事实是当前 commit 下实现究竟是什么样、随开发不断变化的事实，
而非 01 problem.md 文件中的“为什么这是问题、问题基线、必要事实、Assumption / Unknown”，
故内容需随着任务的推进而更新；
已接受的设计约束不随任务的推进而更新，
只在有不同设计约束时更新。

之后就是正式的任务描述了，
每个任务都有一个唯一的编号，
以及一个结果式名称。

任务描述的第一项标明任务的类型，
包括：调查、执行、验证等。
然后是任务的状态，
包括：计划中、待开始、进行中、正审阅、已完成、已阻塞等。

之后是任务的目标，
即完成后可以观察到什么结果。

以及任务所需的参考，
即填写所需参考的01-07文件中的具体描述。

而后，是任务的前置条件，
即为什么现在可以开始；未满足项必须阻塞或转调查。

以及任务的范围，
包括：允许改变的职责区域、必要接缝及理由。

填写完以上这些，
就开始描述任务的具体实现，
包括 Must 和 Must not。
这和 01 中的 goal 、 non-goal 类似，
Must 是必须完成的最小事实，
Must not 是最可能发生的范围扩张或边界破坏。

后续，填写任务的验证、转交、设计变更等。

验证中的内容可直接引用 test-plan.md 文件中的测试项。

Handoff 中填写当前执行任务中发现的需要转交的事项。
Design Delta 中填写设计变更的描述。
这两项若没有可以不填写。

该文档最后填写已完成的任务列表。
包括编号、简要描述、对应版本、必要入口，
其中必要入口是指任务完成时，需要记录的必要信息。
这些信息可以帮助后续学习相关知识，
而 Agent 可直接通过 baseline 中的 commit id 来获取相关信息。

这个文件也体现了“过去压缩、现在详细、未来粗略”的原则。

---
(描述)

反馈回路的核心是 review.md 文件。
可以是人工 review，也可以是 AI review。
Review 只负责裁决和路由，不永久保存最终规则；
若产生架构显著决策，则同步记录到 06 decisions.md。

review 文件通过 DD-xx 编号 + 描述的方式作为标题，
描述需要反馈的内容。

每条反馈内容都需要填写：
Facts 事实是什么？
Decision 决策是什么？
决策包括：Invariant 哪些东西不能牺牲?
Mechanism 用什么机制落实?

上述 SDD 规格驱动开发的相关文档中，
我个人认为最重要的是 01 problem.md 和 09 review.md 文件。
因为这两个文件是最能体现人的意志的文件。
发现现实问题，明确问题是什么，
真实情况是这样的吗，思考问题的原因，
想象出问题被解决时的效果，再以此思考如何解决问题，
以及当现实与期望有差距时如何处理，如何反馈调节。
这些问题在 AI 时代变得更重要了，
这个时代 AI 显著降低了部分代码生成和执行工作的成本，
甚至随着大模型或者其他的 AI 工具越来越强，
很多工具性的工作被逐步替代，
作为人该何去何从？
我个人认为，
相比于做个执行层面的工具人，
应该把自己定位、培养成一个“军师”甚至“君主”，
这种更需要人来思考、判断、决策，
更具主体性的角色。

最后，再分享一个《资治通鉴》中的小故事，
汉昭帝十四岁登上王位，国家大权由霍光掌管，
燕王刘旦、大臣桑弘羊、上官桀嫉妒不满，
一次霍光离开长安去检阅部队，
他们便抓住机会以燕王的口吻写信给汉昭帝，
举报霍光在阅兵过程中擅自调兵、滥用职权，有蓄谋篡位的嫌疑。
但燕王远在北京，而他和霍光在长安，远隔千里，
霍光调动校尉这件事才发生不到十天，
燕王怎么可能这么快就得到消息？
昭帝对照事件发生的时间线，
发现信息对不上，识破了伪造的举报。
放到和 AI /他人协作时也是一样，
不能看到一份看起来很真实的报告就直接认可，
要核对事实、时间线和证据。

同理，无论模型是否具有人的“欺骗意图”，输出的流畅性都不能当成真实性证据。
语言模型本身是概率生成模型，
训练数据与模型认知存在不完备性；
同时某些以准确率为主的训练/评估机制又会奖励“猜一个答案”
而不是承认不知道。
因此模型可能生成流畅但错误的信息。
再加上现在新起的 GEO (生成式引擎优化)手段，
不排除 AI 检索到的信息质量不高甚至是错误的。
因此，在 AI 时代，人的思考、判断、决策能力更加重要。
