# 《小白如何用 SDD 与 AI 开发软件》共用内容母版

状态：系列与演示内容母版 4.2
用途：`01–09` 系列文章、Marp 演示和发布专用工作底稿的共同依据；不约束单文件《SDD 学习实战笔记》的标题、篇幅和章节结构
内容性质：方法说明；开场场景为独立构造的虚构教学推演

## 1. 统一结论

本文所说的 SDD（Spec-Driven Development，规格驱动开发），是先把会决定实现方向的信息变成可以检查和更新的规格，再让人和 AI 按小步任务实施，并用实际证据收口。

内容必须同时讲清两条主线：

- **人的思考过程是时间轴**：当前判断什么、依据什么、何时可以继续。
- **`01–09` 是信息地图**：每类结论由哪份文档保存、被谁引用、什么变化会触发更新；总览由单文件笔记承担，不另设编号。

两条主线通过三个接口连接：

- **读取位置**：作出判断前需要哪些当前事实和已接受约束。
- **写入位置**：判断、证据或待决问题由哪份文档拥有。
- **退出门槛**：进入下一项活动前必须满足什么条件。

核心结论固定为：

> 人的活动产生判断和证据，`01–09` 保存当前有效的信息；AI 通过引用这些信息执行任务，实施反馈再回到信息发生变化的文档。

工作步骤与文档编号不是一一对应关系。步骤可以回退；`06 Decisions` 贯穿多个阶段；`09 Feedback` 负责裁决和路由，不取代 `01–08` 的权威内容。

“小白”指会写代码，但还没有形成稳定规格、架构和验证方法的学习者。内容降低进入门槛，不删除边界、失败、取舍和证据这些会影响实现方向的信息。

## 2. 固定叙事与表达边界

**开头。** 用约 150 字的虚构个人助理愿景说明：一句需求没有给出目标、当前事实、边界、状态、失败和完成证据，因此不能直接指导编码。该场景只出现一次，之后不再沿用，也不在结尾回到它。

**第一部分：人的思考怎样推进一次开发。** 在正文前 20% 内放置“双主线总图”和七步读写表。总图的信息地图逐项说明 `01 Problem` 至 `09 Feedback`，确保编号首次用于流程说明时已经带有含义。七步依次使用 `**1. 明确目标与验收。**` 至 `**7. 验证并同步。**` 这类加粗正文段首，不拆成七个同级标题。

**第二部分：每个判断应该写进哪份文档。** 解释 `01–09` 的唯一信息归属，以九篇系列文章和模板作为阅读入口，并说明 `02–05` 如何共同形成 Architecture Baseline（架构基线）。说明方法名时只在相邻动作第一次出现，并引用直接来源。

**第三部分：AI 怎样读取、执行和回写。** 说明人的裁决责任、AI 的可委托工作和实施边界。四个执行接口在本节重新从 1 编号，依次为 Task Contract、Preflight Brief、实施与 Design Delta、Completion Report；最后给出可复制的公开工作底稿。

**系列文章。** `01–09` 各自保留完整的问题说明、思考顺序、风险扩展、虚构示例、常见错误和更新条件。每篇统一增加系列定位、上一篇、下一篇、总览入口、配套模板和直接延伸来源；`09` 分别使用 Human Review 与 Learning Review Card，不合并成重复模板。

全文遵守以下边界：

- 不使用贯穿全文的案例；孤立字段示例不得组成新的故事线。
- 不展示具体 Agent 框架、模型、数据库、私人项目结构或真实工具 API。
- 不把文档数量写成完成标准，文档深度由风险决定。
- 计划行为使用“预期、计划、待验证”；只有执行过的检查才写为实际结果。
- 系列和演示引用文档时始终同时写出编号和名称，例如 `01 Problem`、`02 Architecture` 至 `05 Failures`。
- 叙述正文直接陈述事实、条件和后果，避免“不是……而是……”“不仅……还……”等固定对照句，以及“真正”“显然”“其实”“本质上”等空泛强调词。技术约束所需的否定应保留明确对象和后果。

## 3. 双主线总图

```text
人的活动：明确目标 → 核实现状 → 设计边界 → 裁决决定 → 推导任务 → 实施变化 → 验证同步
             ↑           │          │          │          │          │          │
             └───────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
                         新证据可以让活动回到信息变化的位置

信息地图：   01–07 目标、架构、契约、失败、决定与验证设计
             08 当前事实、Gap、Task 与实际执行证据
             09 Human Review、Design Delta 裁决与传播
```

图示只表达关系，不把 `01–09` 画成瀑布步骤，也不暗示每次修改都要更新全部文档。

## 4. 七步活动的读写接口

| 人的活动 | 此时要回答的问题 | 主要写入 | 同步检查 | 退出门槛 |
| --- | --- | --- | --- | --- |
| 1. 明确目标与验收 | 为什么改变、得到什么结果、什么不做、需要什么证据 | `01 Problem`，初步 `07 Test Plan` | 单文件总览说明的范围与入口 | Goal、Non-goal、SC 足以判断完成 |
| 2. 核实当前状态 | 当前代码实际怎样、哪些是事实、哪些仍未知 | `08 Tasks` 的 Current Facts；问题基线失真时更新 `01 Problem` | `02 Architecture` 至 `07 Test Plan` 中引用的旧事实 | 已经能够说明 Current State 与 Gap |
| 3. 设计必要边界 | 谁负责状态、运行时怎样协作、模块怎样交互、失败由谁恢复 | 按风险更新 `02 Architecture` 至 `05 Failures`，同步初步 `07 Test Plan` | `01 Problem` 的 Driver 和 SC | 当前增量所需的边界已经明确 |
| 4. 确定关键决定 | 有哪些方案、代价是什么、选择什么、何时重审 | `06 Decisions`；接受后回写受影响的 `01 Problem` 至 `05 Failures`，以及 `07 Test Plan` | 影响清单与验证方式 | 决定已接受，或明确标为 Needs Evidence |
| 5. 推导最小增量 | 当前差距中，下一项可独立验证的结果是什么 | `08 Tasks` 的 Phase、Vertical Slice 和 Task | 引用 `01 Problem` 至 `07 Test Plan` 的具体条目 | Task 目标、范围、禁止项和验证完整 |
| 6. 实施并处理变化 | 新发现属于局部实现、事实变化，还是 Spec 冲突 | `08 Tasks` 记录实施；Design Delta 路由到对应的 `01 Problem` 至 `07 Test Plan` | 必要时由 `09 Feedback` 组织 Review | 没有未处理的关键 Design Delta |
| 7. 验证并同步 | 证据能否证明承诺、哪些事实和规格需要刷新 | `08 Tasks` 保存实际结果，`09 Feedback` 保存评审和传播结论 | `07 Test Plan` 以及受影响的 `01 Problem` 至 `06 Decisions` | 得出 Done、Partial 或 Blocked 结论 |

固定解释：

- `01` 保存相对稳定的问题基线；`08` 保存随实施滚动变化的 Current Facts。
- `06` 是跨阶段的决策记录位置，关键决定在任何阶段出现都可以写入。
- `09` 判断反馈该回到哪里并记录传播结论，不直接覆盖 `01–08`。
- 七步允许回退。调查、实现或验证产生的新证据可以改变更早的判断。

## 5. `01–09` 的唯一信息归属

| 文档 | Owns：唯一负责 | Reads：主要读取 | Emits：主要输出 | Update trigger：更新触发 |
| --- | --- | --- | --- | --- |
| `01 Problem` | 问题基线、Goal、Non-goal、Driver、SC、Unknown、Stop Condition | 用户目标、业务证据、问题现状 | 对设计和验证的目标约束 | 问题、范围、成功标准或稳定基线变化 |
| `02 Architecture` | 术语、系统边界、职责、owner、依赖、不变量、质量驱动 | `01`、当前系统证据 | Architecture Baseline 的静态部分 | 边界、职责、owner、依赖或质量驱动变化 |
| `03 Runtime` | 成功与替代流程、状态机、事件权限、生命周期、提交点、可观测性 | `01/02`、运行证据 | 运行与状态约束 | 流程、状态、事件、生命周期或提交点变化 |
| `04 Contracts` | 跨边界输入输出、前后置条件、状态效果、命令/查询/事件、并发、取消、超时、兼容 | `02/03`、调用方需求 | 调用方可依赖的交互规则 | 公开操作、状态效果或兼容承诺变化 |
| `05 Failures` | 失败分类、检测、传播、恢复 owner、重试、清理、最终状态、Unknown Result | `03/04`、故障证据 | 失败与恢复约束 | 失败路径、恢复责任或最终状态变化 |
| `06 Decisions` | ADR 的背景、方案、决定、后果、取舍、可逆性、验证、逃生口和重审条件 | 任一阶段的关键冲突与证据 | 被接受的关键决定及传播清单 | 上下文、取舍、证据或重审条件变化 |
| `07 Test Plan` | 测试层级、状态反例、Failure/Contract/Architecture Tests、QAS、Fitness Functions、追踪矩阵、Done Gate | `01–06` 的承诺和风险 | 证明方式与完成门槛 | 承诺、风险或可验证性变化 |
| `08 Tasks` | Current Facts、Accepted Constraints、Gap、Phase、Vertical Slice、Task Contract、Preflight、Completion Report | `01–07` 与当前实现 | 近期任务、执行记录和实际证据 | 当前事实、差距、任务顺序或执行结果变化 |
| `09 Feedback` | Human Review、Design Delta 裁决、传播计划、状态区分、Learning Review | `01–08`、实现和验证证据 | Accept/Reject/Deferred/Needs Evidence 与回写路径 | 新反馈需要裁决、传播或沉淀为可复用问题 |

`02–05` 共同形成 Architecture Baseline：

- `02` 规定静态边界、职责、所有权和依赖方向。
- `03` 规定系统怎样运行、状态怎样变化、生命周期怎样结束。
- `04` 规定跨边界可以依赖的交互和状态效果。
- `05` 规定失败怎样被发现、传播、恢复，以及最终留下什么状态。

四者互相引用，不互相复制。只有实际影响当前增量的信息才需要展开。

## 6. 方法来源的使用位置

- 需要表达系统边界时，可从 [C4 model](https://c4model.com/diagrams) 选择有用的视图层级，不要求固定画满四层。
- 需要组织较完整的架构说明时，可参考 [arc42](https://docs.arc42.org/) 的分区思路；本文的 `01–09` 仍是独立整理的信息地图。
- 关键取舍用 [ADR](https://adr.github.io/) 保存一个决定及其理由、取舍和后果。
- 高影响架构问题可借用 [ATAM](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/) 对质量目标、风险、敏感点和取舍点的分析思路，按风险做轻量化的 mini-ATAM，而不声称完成正式 ATAM 评估。
- `07` 可用质量属性场景（Quality Attribute Scenario，QAS）把刺激、环境和可观察响应写具体；Architecture Fitness Functions（架构适应度函数）则把部分架构特征转为可持续运行的检查。[SEI](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)、[Thoughtworks](https://www.thoughtworks.com/content/dam/thoughtworks/documents/books/bk_building_evolutionary_architectures_second_edition_free_chapter.pdf)
- AI 任务流程可对照 [GitHub Spec Kit](https://github.com/github/spec-kit) 的 Spec、Plan、Tasks、Implement 组织方式；本文七步和 `01–09` 不是对其流程的转述。

来源只支持相邻的方法说明，不用于证明本工作流具有未验证的效率或质量效果。

## 7. 追踪、变化与状态

中等以上风险变化使用下面的追踪链：

```text
SC
  → ARCH / INV / ST / API / Failure / ADR
  → TEST
  → TASK References
  → 实际证据
  → Human Review 与定向回写
```

- `01–06` 定义承诺、边界和取舍。
- `07` 用 Traceability Matrix 检查每项承诺是否有证明方式。
- `08` 通过 References 引用相关条目，不重写第二份完整 Spec。
- 实施发现冲突时，`08` 记录 Design Delta，`09` 组织裁决和传播。
- 接受变化后，先更新负责该信息的文档，再刷新 `07/08`。

Design Delta 只指“已接受 Spec 与新证据发生冲突”。普通编码困难、私有算法调整或尚未接受的提案不使用这个名称。路由从信息变化的位置开始：目标回 `01`，边界回 `02`，流程和状态回 `03`，交互回 `04`，失败回 `05`，关键取舍回 `06`，证明方式回 `07`，当前事实或任务顺序回 `08`。

状态必须分开：

- `Draft`：内容仍是提案。
- `Accepted`：人已经接受目标或决定。
- `Propagated`：被接受的决定已经写入受影响的权威文档。
- `Implemented`：代码或系统变化已经完成。
- `Verified`：指定基线上的必要检查已经获得实际证据。

## 8. 人与 AI 的职责边界

人负责确认问题、接受架构与高影响决定、授权高风险动作、处理 Design Delta，并根据实际证据作出 Done、Partial 或 Blocked 结论。

AI 可以承担范围内的代码调查、证据整理、候选方案、影响分析、任务草拟、实现、测试编写和审查。AI 不得把历史文档当作当前事实，不得把未接受提案写成约束，不得超出 Allowed scope，也不得用“文件已生成”或自评代替验证。

外部动作响应丢失时，动作可能已经发生。若接收端没有幂等键或结果查询能力，状态保持 Unknown Result，不能推断为失败并自动重试。

## 9. 公开工作底稿接口

```text
Task：{结果式名称}
状态：Draft / Accepted / Propagated / Implemented / Verified

一、Task Contract
Goal：{本次只交付一个主要结果}
References：{SC、ARCH/INV、ST、API、Failure、ADR、TEST}
Preconditions：{动手前必须成立的事实和决定}
Allowed scope：{允许改变的职责区域}
Must：{必须保持或实现的行为}
Must not：{禁止扩张和不得破坏的边界}
Verify：{需要执行的检查和预期证据}
Design Delta：{遇到哪些 Spec 冲突必须停下评审}
Handoff：{完成后需要交付的记录}

二、Preflight Brief
Baseline：{当前版本和已核实事实}
Planned changes：{本次准备改变什么}
Target files/modules：{预计涉及的区域}
Relevant constraints：{当前任务引用的约束}
Open blockers/Design Deltas：{无，或列出待裁决项}
Readiness：Ready / Blocked

三、Completion Report
Implemented：{实际完成的行为变化}
Files changed：{实际修改范围}
Tests：{实际执行的检查、结果和基线}
Boundary checks：{Must not 与架构边界是否保持}
Design Deltas：{发现、裁决和传播状态}
Remaining risks：{未验证限制和后续风险}
Result：Done / Partial / Blocked
Write-back：{需要刷新哪些 Current Facts、Spec 或状态}
```

Human Review 单独记录 Objective、Evidence Spot Checks、Decision Cards、Adjudication、Go/No-go 与 Propagation Plan，不塞进 Task 正文。

## 10. 媒介约束与验收

单文件笔记：平台中立 Markdown；保留完整方法深度；使用显式文内锚点；除公开参考来源外不链接其他文件。

Marp：16 页主讲加 2 页附录；16:9；暖白、深灰和单一蓝色；全部纯色背景；三幅 Mermaid 图保留 `.mmd` 源文件并生成本地 SVG；Markdown、CSS 和 Mermaid 是可编辑事实源，PDF 和普通 PPTX 是分发副本。

发布前统一检查：

- 七步活动与 `01–09` 同时出现，且没有被写成一一对应或瀑布关系。
- 第一张七步表之前已经逐项解释 `01 Problem` 至 `09 Feedback`；总览内每个文档引用都带有编号和名称。
- 第一部分的七步使用 `1–7` 加粗正文段首，第三部分的四个执行接口重新使用 `1–4` 加粗正文段首。
- 知识点只有一个主要归属，`08` 不复制完整 Spec，`09` 不覆盖权威文档。
- `Draft`、`Accepted`、`Propagated`、`Implemented`、`Verified` 没有混用。
- Test Plan 与实际测试结果明确分开，Unknown Result 没有被改写为确定失败。
- 博客、演示和工作底稿使用同一标题、七步、信息归属与字段。
- 公开内容不包含本机路径、聊天标识、私人仓库、真实账号或可识别开发记录。
- 第三方说明链接到直接来源，不借来源证明未经验证的效果。
- 十篇文章已检查固定对照句和空泛强调词，保留的否定句只承担明确的技术约束。
