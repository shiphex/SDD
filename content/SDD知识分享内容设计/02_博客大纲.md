目标长度：约 4800～5500 个中文字

> 本文件中的标题、字数和章节约束不适用于当前单文件《SDD 学习实战笔记》。当前总览以该笔记正文和 `context.md` 的“单文件笔记方案”为准。

开头预计 260～360 字，不超过全文 8%。先用通俗语言定义本文的 SDD：把会决定实现方向的信息写成可以检查和更新的规格，再让人和 AI 小步实施并用证据收口。随后用约 150 字的虚构个人助理愿景说明，一句话需求缺少目标、当前事实、边界、状态、失败和完成证据。场景在这里结束，正文和结尾不再引用。

## 一、人的思考怎样推进一次开发

预计 1900～2200 字，位于正文开头。前 20% 内按下列顺序呈现两项结构：

1. **双主线总图**：上层为七步活动，下层的信息地图逐项介绍 `01 Problem`、`02 Architecture`、`03 Runtime`、`04 Contracts`、`05 Failures`、`06 Decisions`、`07 Test Plan`、`08 Tasks` 与 `09 Feedback`；强调总览由本文承担，新证据可使活动回退。
2. **七步读写表**：每步同时写“此时判断什么、主要写入、同步检查、退出门槛”。表内每个文档引用继续使用“编号 + 名称”。

七步使用加粗正文段首，不创建新的同级标题或 Markdown 有序列表；可见形式固定为：

`**1. 明确目标与验收。**` 解释 Goal、Non-goal、Success Criteria；主要写 `01 Problem`，在 `07 Test Plan` 放入初步证明方式；退出门槛是目标和成功标准足以判断完成。

`**2. 核实当前状态。**` 从代码、配置、测试和真实接口得到证据；滚动事实写 `08 Tasks`，问题基线失真才更新 `01 Problem`；退出门槛是能说明 Current State 与 Gap。

`**3. 设计必要边界。**` 按风险补 `02 Architecture` 至 `05 Failures`；说明静态边界、运行、契约、失败恢复共同形成 Architecture Baseline；退出门槛是当前增量需要的 owner、交互和恢复责任明确。

`**4. 确定关键决定。**` 比较 Options、Trade-off、Reversibility 与 Verification；写 `06 Decisions`，接受后传播到受影响文档；退出门槛是 Accepted 或 Needs Evidence。

`**5. 推导最小增量。**` 用 `Current State → Target → Gap → Smallest Delta → Evidence` 得到 Vertical Slice；Task 在 `08 Tasks` 引用 `01 Problem` 至 `07 Test Plan`，不复制整份设计。

`**6. 实施并处理变化。**` AI 只在 Allowed scope 与已接受约束内实施；区分局部实现问题、事实变化和 Design Delta；后者仅指已接受 Spec 与新证据冲突。

`**7. 验证并同步。**` 从成功标准核对实际证据，给出 Done、Partial 或 Blocked；定向刷新拥有信息的文档，不机械重写全部规格。

本节穿插说明三处易混关系：

- `01 Problem` 保存相对稳定的问题基线，`08 Tasks` 保存滚动 Current Facts。
- `06 Decisions` 贯穿全过程，编号只表示信息位置。
- `09 Feedback` 组织裁决、路由和传播，不替代 `01 Problem` 至 `08 Tasks`。

## 二、每个判断应该写进哪份文档

预计 1400～1600 字。先说明本文同时承担总览和系列入口，不另设编号；再给 `01–09` 权威信息表，表格至少含文章、配套模板、Owns、Reads、Emits、Update trigger：

- `01 Problem`：问题、目标、范围、Driver、SC、Unknown、Stop Condition。
- `02 Architecture`：静态边界、职责、owner、依赖、不变量与质量驱动。
- `03 Runtime`：流程、状态、事件权限、生命周期、提交点与可观测性。
- `04 Contracts`：输入输出、前后置条件、状态效果、并发、取消、超时和兼容。
- `05 Failures`：失败分类、检测、传播、恢复 owner、最终状态和 Unknown Result。
- `06 Decisions`：关键取舍、后果、可逆性、验证和重审条件。
- `07 Test Plan`：证明方式、反例、追踪矩阵和 Done Gate。
- `08 Tasks`：Current Facts、Gap、近期 Task、Preflight 和 Completion Report。
- `09 Feedback`：Human Review、Design Delta 裁决、传播与学习反馈。

表格中的 `01–09` 分别链接到 `05_SDD博客系列文章/` 内的九篇完整草稿。`01–08` 链接各自模板，`09` 链接 Human Review 和 Learning Review Card。表后给出四条选读路径：初次学习、开始设计、拆分 Task、审核报告或设计变化。

再解释 `02–05` 如何共同形成 Architecture Baseline，避免把 Architecture 缩成目录结构或一张组件图。

方法来源只在相邻动作首次出现：

- 系统边界提 [C4](https://c4model.com/diagrams)。
- 文档组织提 [arc42](https://docs.arc42.org/)。
- 关键决定提 [ADR](https://adr.github.io/) 与 [ATAM](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)；本文只借用 ATAM 的风险、敏感点和取舍点思路做 mini-ATAM。
- 验证提质量属性场景（QAS）和 [Architecture Fitness Functions](https://www.thoughtworks.com/content/dam/thoughtworks/documents/books/bk_building_evolutionary_architectures_second_edition_free_chapter.pdf)。
- AI 任务组织提 [GitHub Spec Kit](https://github.com/github/spec-kit)，明确本文七步是独立整理。

本节展示追踪链：

```text
SC
  → ARCH / INV / ST / API / Failure / ADR
  → TEST
  → TASK References
  → 实际证据
  → Human Review 与定向回写
```

说明低风险任务可以把有关信息合并在一份短 Spec 中，但信息归属仍按地图判断；文件数量不等于完成程度。

## 三、AI 怎样读取、执行和回写

预计 1600～1800 字。先界定职责：人负责问题、架构、关键裁决、高风险授权和最终验收；AI 可承担调查、证据整理、备选方案、影响分析、任务草拟、范围内实施、测试编写和审查。

按一次任务的四个接口展开。本节重新从 1 编号，并使用加粗正文段首：

`**1. Task Contract：定义本次允许范围。**` Goal、References、Preconditions、Allowed scope、Must、Must not、Verify、Design Delta、Handoff。

`**2. Preflight Brief：确认能否开始实施。**` Baseline、Planned changes、Target files/modules、Relevant constraints、Open blockers/Design Deltas、Readiness。

`**3. 实施与 Design Delta：处理新证据。**` 只在已接受 Spec 被新证据推翻时停下评审；普通实现困难留在 Code 与当前 Task。外部动作响应丢失且不能查询时保持 Unknown Result。

`**4. Completion Report：用事实结束任务。**` 记录实际行为、修改范围、测试结果和基线、边界检查、遗留风险、结论与定向回写；Human Review 独立保存裁决与传播计划。

状态表必须包含并区分 `Draft`、`Accepted`、`Propagated`、`Implemented`、`Verified`。接受不等于传播，传播不等于实现，实现不等于验证。

结尾直接给出可复制的空白公开工作底稿，由 Task Contract、Preflight Brief 和 Completion Report 三部分组成。Human Review 不塞进 Task 正文。最后一句落在实际使用动作：先写 Goal 与 Current Facts，再从 Gap 选一项最小变化；若新证据改变规格，就回到负责该信息的位置。
