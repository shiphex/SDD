## 3. 两条主线怎样结合

人的思考过程与 `01–09` 分别描述活动时间轴和信息位置，两者共同组成一套工作方法。

- **活动回答“现在做什么”**。它有先后顺序，也允许回退。
- **文档回答“结论放在哪里”**。它按信息职责划分，不随活动顺序改变。
- **Task 回答“下一项实际变化是什么”**。它引用上游约束，不复制另一套 Spec。
- **Feedback 回答“新证据应该修改哪一层”**。它负责路由，不取代权威文档。

可以把整体关系理解为：

```text
人的活动
  明确目标 → 核实现状 → 设计边界 → 裁决取舍
      → 推导增量 → 实施 → 验证与同步

信息落点
  01–07：当前有效的规格、设计、决定与验证方法
  08：当前事实、近期任务与实际完成记录
  09：评审、变化路由与思维反馈方法
```

这条路径允许回退。后面的实现证据可以推翻前面的假设，变化必须先回到负责该信息的文档，再定向传播到受影响的下游内容。

## 4. 七步活动与 `01–09` 的读写关系

博客和演示共用下面的主表。讲解每一步时，需要同时交代人在判断什么、结论写到哪里、还要核对什么以及何时可以继续。

| 人的活动 | 此时要回答的问题 | 主要写入 | 同步检查 | 退出门槛 |
| --- | --- | --- | --- | --- |
| 1. 明确目标与验收 | 为什么改变、得到什么结果、什么不做、需要什么证据 | `01 Problem`，初步 `07 Test Plan` | 单文件总览说明的范围与入口 | Goal、Non-goal、SC 足以判断完成 |
| 2. 核实当前状态 | 当前代码实际怎样、哪些是事实、哪些仍未知 | `08 Tasks` 的 Current Facts；问题基线失真时更新 `01 Problem` | `02 Architecture` 至 `07 Test Plan` 中引用的旧事实 | 已经能够说明 Current State 与 Gap |
| 3. 设计必要边界 | 谁负责状态、运行时怎样协作、模块怎样交互、失败由谁恢复 | 按风险更新 `02 Architecture` 至 `05 Failures`，同步初步 `07 Test Plan` | `01 Problem` 的 Driver 和 SC | 当前增量所需的边界已经明确 |
| 4. 确定关键决定 | 有哪些方案、代价是什么、选择什么、何时重审 | `06 Decisions`；接受后回写受影响的 `01 Problem` 至 `05 Failures`，以及 `07 Test Plan` | 影响清单与验证方式 | 决定已接受，或明确标为 Needs Evidence |
| 5. 推导最小增量 | 当前差距中，下一项可独立验证的结果是什么 | `08 Tasks` 的 Phase、Vertical Slice 和 Task | 引用 `01 Problem` 至 `07 Test Plan` 的具体条目 | Task 目标、范围、禁止项和验证完整 |
| 6. 实施并处理变化 | 新发现属于局部实现、事实变化，还是 Spec 冲突 | `08 Tasks` 记录实施；Design Delta 路由到对应的 `01 Problem` 至 `07 Test Plan` | 必要时由 `09 Feedback` 组织 Review | 没有未处理的关键 Design Delta |
| 7. 验证并同步 | 证据能否证明承诺、哪些事实和规格需要刷新 | `08 Tasks` 保存实际结果，`09 Feedback` 保存评审和传播结论 | `07 Test Plan` 以及受影响的 `01 Problem` 至 `06 Decisions` | 得出 Done、Partial 或 Blocked 结论 |

### 三个必须讲清的关系

1. **`01 Problem` 与 `08 Tasks` 的事实不同。** `01 Problem` 保存相对稳定的问题背景和设计基线；`08 Tasks` 保存随实施滚动变化、带版本证据的 Current Facts。
2. **`06 Decisions` 贯穿全程。** 编号只表示信息位置。目标澄清、架构设计、失败分析和实现调查都可能产生需要记录的 ADR。
3. **`09 Feedback` 只负责评审与路由。** 它判断反馈应写回哪里，但不直接覆盖 `01 Problem` 至 `08 Tasks` 中的权威结论。

## 5. `01–09` 的知识归属

每份文档拥有一种信息。其他文档只引用编号和当前任务需要的摘要，避免同一规则出现多个版本。

| 文档 | 权威保存的内容 | 必须覆盖的知识点 |
| --- | --- | --- |
| `01 Problem` | 为什么做以及什么算成功 | Problem、Goal、Non-goal、Architecture Drivers、Success Criteria、Unknowns、Stop Condition |
| `02 Architecture` | 系统的静态边界和责任归属 | Glossary、C4/System Boundary、Component Responsibility、Owns/May/Must not、状态和生命周期 owner、依赖方向、架构不变量、质量驱动、mini-ATAM |
| `03 Runtime` | 系统运行时的协作和状态变化 | Success Flow、Alternate Flow、Sequence、数据流与控制流、State Machine、事件权限、生命周期、Commit Point、Observability |
| `04 Contracts` | 跨边界可以依赖的交互规则 | Purpose、Input/Output、Preconditions/Postconditions、State Effect、Command/Query/Event、幂等、并发、取消、超时、兼容、Runtime Invariants、Must not |
| `05 Failures` | 失败分类、传播和恢复责任 | Failure Policy、错误类别、Detection、Propagation、Recovery Owner、Recovery、Final State、Unknown Result、重试预算、级联失败 |
| `06 Decisions` | 关键取舍及其理由 | ADR 的 Context、Options、Decision、Consequences、Trade-off、Reversibility、Verification、Escape Hatch、Review Trigger、Propagation |
| `07 Test Plan` | 用什么证据证明承诺成立 | 测试层级、状态反例、Failure Tests、Contract Tests、Architecture Tests、QAS、Fitness Functions、Traceability Matrix、Done Gate |
| `08 Tasks` | 从当前事实到目标的近期变化 | Current Facts、Accepted Design Constraints、Gap、Phase、Vertical Slice、调查型与实现型 Task、Task Contract、Preflight、Completion Report、Done、历史压缩 |
| `09 Feedback` | 怎样评审、路由变化并形成学习 | Human Review、Design Delta、裁决语义、传播计划、状态区分、Learning Review、Human-first/AI-second、知识升级条件 |

### 每份文档的统一信息接口

后续介绍 `01–09` 时，不机械复述目录，而是说明四件事：

- **Owns**：这份文档唯一负责定义什么。
- **Reads**：形成判断前需要读取哪些上游信息和证据。
- **Emits**：它为哪些下游活动提供什么约束或引用。
- **Update trigger**：哪些变化必须回来更新，哪些局部实现变化不需要更新。

这样可以把“人怎样思考”和“知识怎样保存”放在同一说明框架内。

## 6. 追踪、变化与完成状态

### 6.1 从目标到证据的追踪链

中等以上风险的变化使用下面的追踪关系，避免知识点在拆任务时丢失：

```text
SC
  → ARCH / INV / ST / API / Failure / ADR
  → TEST
  → TASK References
  → 实际证据
  → Human Review 与定向回写
```

- `01–06` 定义承诺、边界和取舍。
- `07` 使用 Traceability Matrix 检查承诺是否都有证明方式。
- `08` 的 Task 通过 References 引用相关条目，不重新解释完整设计。
- 实施发现冲突时，`08` 记录 Design Delta，`09` 组织裁决和传播。
- 接受变化后，先更新真正拥有该信息的文档，再刷新 `07/08`。

低风险任务不强制为所有条目分配编号，但仍需说明目标、当前事实、范围、禁止项和验证。涉及跨模块、公开契约、持久化、复杂状态、外部副作用或难回退决定时，补齐相应追踪关系。

### 6.2 Design Delta 的路由

Design Delta 只用于“已接受 Spec 在新证据下无法继续成立”，不作为普通实现困难的名称。

| 新发现影响什么 | 主要回写位置 | 常见下游检查 |
| --- | --- | --- |
| 问题、目标、范围或成功标准 | `01` | `02–08` |
| 边界、职责、owner 或依赖方向 | `02`，必要时 `06` | `03–08` |
| 流程、状态、事件或生命周期 | `03` | `04/05/07/08` |
| 输入输出、调用权限或兼容承诺 | `04` | `05/07/08` |
| 失败分类、未知结果或恢复责任 | `05` | `04/07/08` |
| 机制选择及其取舍 | `06` | 实际受影响的 `01–08` |
| 证明方式无法验证承诺 | `07` | `08`，必要时上游 Spec |
| 实施顺序、范围或当前事实 | `08` | 当前与后续 Task |
| 局部算法或私有结构 | Code 与当前 Task | 定向验证，不更新无关 Spec |

只从真正变化的位置向下做影响分析，不机械重写全部文档，也不让代码差异成为未声明的新架构。

### 6.3 状态必须分开

| 状态 | 含义 |
| --- | --- |
| `Draft` | 当前内容仍是提案，尚未被接受 |
| `Accepted` | 人已经接受目标或决定 |
| `Propagated` | 接受的决定已经写入受影响的权威文档 |
| `Implemented` | 代码或系统变化已经完成 |
| `Verified` | 必需检查已经在指定基线上获得实际证据 |

接受决定不代表已经实现；测试计划存在不代表验证已经通过。

### 6.4 Human Review 的位置

Human Review 是人的判断过程与文档反馈过程的连接点。按风险选择 Problem Review、Design Review、Task Preflight Review、Design Delta Review 或 Completion Review。

评审至少记录：

- Objective 与适用基线。
- 抽查的关键事实和证据。
- Conflict、Options、Decision、Why、Trade-off 与 Reversibility。
- Accept、Reject、Deferred 或 Needs Evidence。
- GO、Conditional GO 或 NO-GO，以及允许继续的具体范围。
- 需要传播到哪些 `01–08` 文档。

## 7. 公开工作底稿接口

公开工作底稿用于展示 `01–09` 怎样共同控制一项近期变化。它不替代完整知识库，也不要求低风险任务分别创建九份文件。

```text
Task：{结果式名称}
状态：Draft / Accepted / Propagated / Implemented / Verified

一、Task Contract
Goal：{本次只交付一个主要结果}
References：{SC、ARCH/INV、ST、API、Failure、ADR、TEST}
Preconditions：{动手前必须成立的事实和决定}
Allowed scope：{允许改变的职责区域}
Must：{必须保持或实现的行为}
Must not：{禁止扩张和不得破坏的边界}
Verify：{需要执行的检查和预期证据}
Design Delta：{遇到哪些 Spec 冲突必须停下评审}
Handoff：{完成后需要交付的记录}

二、Preflight Brief
Baseline：{当前版本和已核实事实}
Planned changes：{本次准备改变什么}
Target files/modules：{预计涉及的区域}
Relevant constraints：{当前任务引用的约束}
Open blockers/Design Deltas：{无，或列出待裁决项}
Readiness：Ready / Blocked

三、Completion Report
Implemented：{实际完成的行为变化}
Files changed：{实际修改范围}
Tests：{实际执行的检查、结果和基线}
Boundary checks：{Must not 与架构边界是否保持}
Design Deltas：{发现、裁决和传播状态}
Remaining risks：{未验证限制和后续风险}
Result：Done / Partial / Blocked
Write-back：{需要刷新哪些 Current Facts、Spec 或状态}
```

Human Review 不塞进 Task 正文。需要评审时，单独记录 Objective、Evidence Spot Checks、Decision Cards、Adjudication、Go/No-go 和 Propagation Plan。

## 8. 单文件笔记方案

### 8.1 基本要求

- 文件名固定为 `SDD学习实战笔记.md`，标题固定为《SDD 学习实战笔记》。
- 使用平台中立的 Markdown，不设置硬性字数上限，保留原长笔记的方法深度、模板、清单和学习附录。
- 采用“总览与速查、`01–07` Spec 编写、`08 Tasks` 执行、`09 Feedback` 闭环、实战训练、术语与外部方法附录”的结构。
- `09 Feedback` 独立负责 Design Delta、Human Review、裁决和传播，不塞回 `08 Tasks`。
- 目录和交叉引用使用显式 ASCII 锚点。除公开参考来源外，笔记中的链接只允许跳转到本文锚点。
- 外部方法只说明借鉴关系，不把七步工作流和 `01–09` 信息结构归因于第三方。

### 8.2 内容边界

- 以通用工程语言解释方法，不暴露本机路径、私人项目、内部来源关系或可识别开发记录。
- 文中业务名称、接口、状态和数值均为独立构造的虚构教学示例。
- 不把文档数量写成完成标准；按风险裁剪记录深度。
- 设计预期使用“预期、计划、待验证”；实际结果必须有当前基线上的证据。
- 叙述正文直接说明事实、条件和后果，避免固定对照句、空泛强调和无依据效果承诺。

### 8.3 配套导航

- `01–09` 系列文章和模板继续保留，并把总览入口指向单文件笔记。
- 单文件笔记不反向依赖系列文章、模板或 V2 文件，下载一个文件即可完整阅读。
- 旧总览博客和旧博客大纲不再作为当前发布入口；大纲仅保留历史设计状态。

## 9. Marp 演示方案

### 9.1 产物与技术边界

- 使用 Marp Markdown 作为内容和版式的可维护源稿。
- 使用独立主题 CSS 控制 16:9、字体、颜色、间距和页面层级。
- Mermaid 图保留 `.mmd` 源文件，生成本地 SVG 后嵌入 Marp，避免依赖演示现场的远程服务。
- 当前交付为 Markdown、CSS、Mermaid 源文件和本地 SVG，不生成 PDF。
- 普通 PPTX 与实验性的 editable PPTX 均不在当前交付范围内。
- Marp 和 Mermaid 的具体版本在制作时固定，并在导出前核对官方说明。

### 9.2 视觉规范

- 16:9。
- 全部使用纯色背景，不使用背景图片、装饰插图、渐变或纹理。
- 暖白为主要背景，深灰正文，单一蓝色强调；封面可以使用纯蓝背景。
- 使用本机可稳定渲染中文的无衬线字体，不依赖远程字体。
- 标题页标题约 42pt，页面标题不低于 32pt，正文原则上不低于 18pt。
- 除页标题外，每页最多展示 7 个可见文本行或行组；超出时拆页，不通过缩小字号解决。
- 每页只推进一个主要判断，减少卡片、标签、页脚碎片和重复说明。
- 不展示代码、终端、真实产品界面或具体 API。
- 页面在不看讲者备注时也能理解主要结论；备注只补充解释、转场和来源。

### 9.3 页面顺序

主讲 17 页，以《模板》和《SDD 学习实战笔记》为两条内容轴线。《讲解稿》只承担口播，不决定页面切分，也不向页面补充故事、动机铺垫或角色比喻。页面按以下顺序组织：

1. 封面与两条轴线：活动时间轴和 `01–09` 信息地图。
2. 完整闭环与文档总览：`01–07 Spec`、`08 Tasks`、`09 Feedback` 的关系。
3. `01 Problem` 至 `07 Test Plan`：逐页呈现模板字段，并用实战笔记解释字段之间的推导关系。
4. 追踪链：从 Success Criteria、设计约束和 Test Plan 连接到 Task 与实际证据。
5. `08 Tasks`：Current Facts、Target、Gap、Task Contract 和滚动规划。
6. `09 Feedback`：Human Review、Design Delta 与定向传播。
7. 完成状态：区分 Draft、Accepted、Propagated、Implemented 与 Verified，并用 Done Gate 收束。

页面只保留观众需要看到的结构、字段和关系。完整解释、转场和案例放在《讲解稿》中，不重复写入页面。

### 9.4 Mermaid 图

使用两幅 Mermaid 图和若干原生 Markdown / HTML 结构图：

1. **Spec 到证据的追踪链**：展示 SC、设计约束、TEST、TASK、实际证据和 Review 的关系。
2. **Design Delta 与反馈回写循环**：展示实施证据怎样经过 Human Review 回到正确文档，再传播到 Task 和验证。
3. **原生结构图**：用于两条轴线、`01–09` 信息地图、Current–Gap–Target 和完成状态，保持文本清楚且易于维护。

图示保持平面、少节点、少交叉线。`01–09` 的完整知识清单使用可编辑表格，不塞进流程图。
