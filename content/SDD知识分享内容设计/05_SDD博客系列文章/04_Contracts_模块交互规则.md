# 04 Contracts：模块交互规则

> SDD 系列第 4 篇｜上一篇：[03 Runtime](03_Runtime_运行流程状态与生命周期.md)｜下一篇：[05 Failures](05_Failures_失败语义与恢复责任.md)｜总览：[SDD 学习实战笔记](../SDD学习实战笔记.md)｜配套：[04 Contracts 模板](templates/04-contracts模板.md)

函数签名只能说明“怎样调用”，不能完整说明“调用方可以依赖什么”。本文把输入输出、状态效果、失败、并发、取消和兼容要求收敛为跨边界契约。

## 1. 本文回答的核心问题

`04` 回答：模块之间允许怎样交互，调用方可以依赖哪些输入、输出、状态效果和失败语义，以及接口中明确不应出现哪些能力。

结构图帮助理解，契约负责精确。契约只承诺调用方需要依赖的行为，不提前暴露私有实现。

## 2. 为什么需要这份文档

如果接口只有函数签名，调用方仍然不知道：

- 调用前必须满足什么条件。
- 成功后哪些状态一定改变。
- 失败时是否可能已经产生副作用。
- 同一个请求能否安全重放。
- 谁有权限调用。
- 取消和超时分别意味着什么。

这些问题若留到编码时临时决定，不同模块会形成互相冲突的假设。Contract（契约）把跨边界的可依赖行为固定下来，并成为测试和 Task 验收的共同依据。

## 3. 写作前需要哪些输入

- `01` 的成功标准和兼容约束。
- `02` 的模块边界、所有权和依赖方向。
- `03` 的状态、事件、主链、失败分支和提交点。
- `05` 中已知的领域失败或恢复要求。
- 当前公开接口以及调用方的实际使用证据。

候选签名可以先列为提案，但在决定接受前不要把它写成现有事实。

## 4. 设计时应依次思考哪些问题

### 4.1 先写 Purpose 与 Ownership

每个契约先回答：

- **Purpose（目的）**：这个边界为什么存在？
- **Ownership（所有权）**：谁提供、谁持有、谁控制其生命周期？
- **Consumers（使用者）**：哪些调用方可以依赖它？

如果两个接口目的相同但所有权不同，先回到 `02` 检查边界是否重复。

### 4.2 为每个公开操作回答十问

至少覆盖：

1. 操作的语义是什么？
2. 输入是什么，哪些字段必需？
3. 输出是什么，调用方可依赖哪些字段？
4. 前置条件是什么？
5. 成功后的后置条件是什么？
6. 会改变哪些权威状态？
7. 可能出现哪些领域失败？
8. 是否幂等，幂等范围和键是什么？
9. 取消或超时后结果如何解释？
10. 谁允许调用，谁明确不允许调用？

简单的纯函数可以省略不适用项；外部副作用或跨进程操作应完整回答。

### 4.3 区分命令、查询和事件

- **Command（命令）**：请求系统尝试改变状态，可能被拒绝。
- **Query（查询）**：读取权威状态或派生视图，不应改变领域状态。
- **Event（事件）**：只报告已经发生的事实，不承载隐藏返回值或请求执行语义。

将查询和写入混在同一操作，会让缓存、重试和权限语义变得含糊。

### 4.4 写清前置与后置条件

前置条件是调用方必须满足、提供方可以校验的条件。后置条件是操作成功返回后保证成立的事实。

不要把内部算法步骤写成后置条件。调用方不需要依赖“先写表 A 再写表 B”，除非顺序本身是跨边界承诺。

### 4.5 对齐状态效果与领域失败

每个会改变状态的操作都要能映射到 `03` 的合法事件和转移。每个预期可处理的业务拒绝都应有稳定的领域失败，调用方无需解析日志或任意异常文本。

Programmer error（编程错误）与 domain failure（领域失败）不要混为一类。前者通常表示调用或实现违反内部不变量，后者是契约预期的一部分。

### 4.6 明确幂等、重复和并发

“幂等”必须带范围：

- 哪个操作幂等？
- 在多长时间或哪个业务生命周期内？
- 使用什么幂等键？
- 同键不同载荷怎样处理？
- 并发的重复请求返回同一结果，还是冲突？

只写“接口幂等”不足以指导实现或验证。

### 4.7 分开超时、取消与失败

- **失败**：系统拥有证据表明操作没有满足契约。
- **超时**：等待超过约定时间，不一定知道远端结果。
- **取消**：调用方请求停止后续工作，不保证已提交动作能够撤销。

外部动作响应丢失时，契约需要返回“未知”、查询句柄或其他可以诚实表达不确定性的结果。

### 4.8 写 Must NOT 列表

为高风险边界列出“不应存在的能力”，例如：

- 只读查询接口不得暴露状态修改操作。
- 编排层不得创建底层持久化连接。
- 外部适配器不得决定领域状态转移是否合法。

Must NOT 应与 `02` 的边界一致，并在 `07` 中选择适当的自动化或评审检查。

### 4.9 处理兼容性

公开契约变化时说明：

- 哪些旧调用方仍需支持。
- 新旧语义是否可以并存。
- 版本或迁移窗口是什么。
- 不兼容变化如何被发现和发布。

建议目录和类名可以放在实施备注中，但要标为非契约内容。

## 5. 最小内容与高风险扩展内容

### 5.1 最小内容

- Purpose / Ownership / Consumers
- Public Operations
- 输入与输出
- 前置、后置和状态效果
- 领域失败
- Must NOT

### 5.2 高风险扩展

- 幂等键与重复请求语义
- 并发冲突和版本检查
- 超时、取消与结果未知
- 授权和信任边界
- 兼容与迁移策略
- Runtime Invariants（运行时不变量）

## 6. 独立虚构示例

> 教学推演：以下“桌游活动报名器”完全虚构，仅用于说明契约；没有真实接口或验证结果。

`RegistrationBook` 是报名状态 owner。公开操作之一为：

```text
reserve_session(command) -> ReservationResult
```

### Purpose

在指定活动仍有名额时，为参与者创建一次报名。

### Input

- `request_id`：调用方生成的幂等键。
- `session_id`：活动标识。
- `participant_alias`：本案例中的虚构显示名。

### Preconditions

- `request_id` 非空。
- 活动存在且尚未结束报名。

### Postconditions

- 成功后存在一条可查询的报名记录。
- 同一 `request_id` 与相同载荷重复调用，返回同一报名结果。

### State effect

- 只有 `RegistrationBook` 可以扣减剩余名额并创建报名。

### Domain failures

- `SessionNotFound`
- `RegistrationClosed`
- `NoSeatAvailable`
- `IdempotencyConflict`：同一 `request_id` 携带不同载荷。

### Must NOT

- 查询接口不得补报名或扣减名额。
- 通知适配器不得直接修改报名状态。

该契约尚未指定数据结构、数据库或类布局。它们只有在影响上述承诺时才需要升级为设计决定。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| 只有函数签名 | 失败或重放后调用方能依赖什么？ | 补齐语义和状态效果 |
| 返回任意字符串错误 | 调用方如何稳定分支处理？ | 使用领域失败类型或结果 |
| 幂等没有范围 | 同键不同载荷怎样处理？ | 定义键、窗口和冲突语义 |
| 超时等同于失败 | 远端动作可能已经提交吗？ | 表达未知或提供查询 |
| 契约与状态机不一致 | 操作触发的事件在 `03` 合法吗？ | 统一状态、事件和 Guard |
| 接口不断增加越界能力 | 哪项能力违反 owner 或 Must not？ | 删除或迁移到正确边界 |

## 8. 与其他文档的输入、输出和更新关系

- 从 `02` 接收边界、owner 和依赖方向。
- 从 `03` 接收状态、事件、Guard 和提交点。
- 与 `05` 共同定义失败、重试和恢复的跨边界语义。
- 输出给 `07`：contract test、状态测试和兼容测试依据。
- 输出给 `08`：Implementation Task 必须保持的行为边界。
- 改变公开承诺的取舍应记录到 `06`。

## 9. 什么变化会触发本文更新

- 公开操作、输入、输出或调用权限改变。
- 前置、后置、状态效果或领域失败改变。
- 幂等、并发、取消、超时或未知结果语义改变。
- 兼容承诺和迁移窗口改变。
- `02/03/05` 的接受性变化使现有契约失效。

不影响调用方依赖的私有重构通常不更新 `04`。
