# 06 Decisions：设计取舍与决策记录

> SDD 系列第 6 篇｜上一篇：[05 Failures](05_Failures_失败语义与恢复责任.md)｜下一篇：[07 Test Plan](07_Test_Plan_验证设计与完成条件.md)｜总览：[SDD 学习实战笔记](../SDD学习实战笔记.md)｜配套：[06 Decisions 模板](templates/06-decisions模板.md)

当多个方案都能工作时，设计需要保存选择依据、主动接受的代价和重审条件。决定可能在任何阶段出现，无须等到“第六步”。

## 1. 本文回答的核心问题

`06` 回答：为什么选择当前方案，比较过哪些候选方案，接受了什么代价，哪些问题仍未决定，以及在什么条件下需要重审。

`06` 统一记录设计决定，贯穿整个流程。决定可以在任何阶段产生。

## 2. 为什么需要这份文档

只记录最终方案，几个月后往往无法判断：

- 当时是基于什么事实和约束做决定。
- 被拒绝的方案为什么不合适。
- 哪些坏处是已知且主动接受的。
- 决定适用到什么时候。
- 新证据出现后，应继续坚持还是重新比较。

[Architecture Decision Record](https://adr.github.io/)（架构决策记录，简称 ADR）保存决定链；聊天纪要无法替代它。决定链让未来的修改者能够分辨“有理由的约束”和“可以自由替换的历史机制”。

## 3. 写作前需要哪些输入

- 要解决的具体冲突或张力。
- 与决定直接相关的当前事实及证据。
- `01` 的 Drivers、Non-goal 和成功标准。
- `02–05/07` 中受到影响的规则。
- 至少两个真实可行的候选方案；若只有一个，也要说明为什么其他方向不成立。
- 当前授权范围和需要 Human Review 的门槛。

不要用未经核实的事实给候选方案打分。

## 4. 设计时应依次思考哪些问题

### 4.1 先分开 Invariant 与 Mechanism

- **Invariant（不变量）**：不能牺牲的性质，例如“每次任务只能有一个权威终态”。
- **Mechanism（机制）**：当前用来满足不变量的方法，例如“使用单一状态存储”。

不变量往往更稳定，机制可能随规模和证据变化。把机制误写成永恒原则会制造不必要的锁定。

### 4.2 判断是否值得写 ADR

推荐在以下情况写 ADR：

- 影响公开契约、状态所有权或持久化。
- 难以回退或影响多个模块。
- 候选方案之间有重要质量取舍。
- 决定会约束多项后续任务。
- 团队很可能再次提出同一问题。

局部私有算法、容易替换的库调用或普通命名通常留在 Task 或代码中。

### 4.3 使用最小充分决定

Minimum Sufficient Decision（最小充分决定）指：只裁决当前增量必须稳定的部分，把不影响当前工作的细节留到获得更多证据时决定。

配合两个问题：

- **Decision Horizon（决定视界）**：这项决定至少需要支撑到哪个阶段？
- **Dependency（依赖关系）**：哪些工作真的依赖这个决定？

未决问题只阻塞依赖它的工作，不应冻结整个项目。

### 4.4 比较候选方案

比较维度应来自 `01` 的 Driver 和当前风险，例如：

| 维度 | 要问的问题 |
| --- | --- |
| 正确性 | 能否保持核心不变量？ |
| 兼容性 | 旧调用方或数据是否仍可用？ |
| 复杂度 | 引入多少新概念和运维责任？ |
| 可测试性 | 关键承诺能否被独立验证？ |
| 可恢复性 | 失败后能否查询、重试或补偿？ |
| 可逆性 | 判断错误后改回的成本多大？ |
| 影响范围 | 多少模块和使用者会受影响？ |

分数可以帮助讨论，但不能取代文字理由。候选方案被拒绝的原因应能追溯到事实或优先级。

### 4.5 用 mini-ATAM 找风险和取舍

mini-ATAM 是对 [SEI Architecture Tradeoff Analysis Method](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/) 中质量目标、风险、敏感点和取舍点分析思路的轻量化使用，不代表完成了正式 ATAM 评估。这里关注：

- Driver：最重要的质量目标。
- Tactic：候选方案采用的策略。
- Sensitivity point：结果对哪个设计点特别敏感。
- Trade-off point：同一设计点改善一个质量却损害另一个质量。
- Risk：在当前证据下仍可能失败的地方。

评估过程用于让隐含代价进入裁决，无需计算一个“客观总分”。

### 4.6 按可逆性与影响范围设置审查

| 可逆性 | 影响范围 | 推荐审查强度 |
| --- | --- | --- |
| 高 | 小 | 快速决定，保留最少记录 |
| 高 | 大 | 关注传播范围和回退步骤 |
| 低 | 小 | 重点验证不可逆点 |
| 低 | 大 | 最严格的证据、方案比较和 Human Review |

这种风险适配方式用于分配评审力度，不应被当作机械评分公式。

### 4.7 写完整 ADR

一份 ADR 至少包含：

- `Status`：Proposed / Accepted / Rejected / Deferred / Superseded。
- `Context`：冲突、事实和约束。
- `Decision`：接受的方案及边界。
- `Alternatives`：候选方案与拒绝理由。
- `Consequences`：正面、负面和新增责任。
- `Verification`：怎样证明决定有效。
- `Escape Hatch`：判断错误时怎样退出。
- `Review Trigger`：什么新证据触发重审。

`Deferred` 必须写重审条件，不等于把问题永久丢进待办列表。

### 4.8 让决定产生验证

每个被接受的决定都应能回答“什么证据会支持或反驳它”。例如：

- 复用决定 → 检查没有复制第二套规则。
- 隔离决定 → 验证两个实例互不污染。
- 兼容决定 → 旧调用路径的契约测试仍通过。
- 简化决定 → 检查没有引入被排除的新子系统。

如果完全无法设计验证，决定可能仍然太抽象。

## 5. 最小内容与高风险扩展内容

### 5.1 最小内容

- ID 与标题
- Status
- Context
- Decision
- Alternatives
- Consequences
- Verification

### 5.2 高风险扩展

- 证据基线
- mini-ATAM 风险表
- 可逆性与影响范围
- 回退或迁移计划
- Human Review 来源
- 重审条件与决策视界
- 对 `01–08` 的传播清单

## 6. 独立虚构示例

> 教学推演：以下“图书漂流点库存同步”完全虚构，只用于说明 ADR；没有真实实现或测试结果。

### ADR-001：离线登记的冲突处理位置

**Status**：Accepted（教学示例中的假定状态）

**Context**：两个志愿者终端可能离线登记同一本书的取走动作。核心不变量是“一本书在同一时刻最多有一个有效持有人”。

**Alternatives**：

| 方案 | 不变量 | 离线可用 | 复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| A. 终端本地直接决定 | 无法跨终端保证 | 高 | 低 | 拒绝 |
| B. 恢复连接后由中央 Ledger 裁决 | 可由单一 owner 保证 | 中 | 中 | 接受 |
| C. 禁止所有离线登记 | 可保证 | 低 | 低 | 拒绝，违反离线 Driver |

**Decision**：终端离线时只记录“待裁决意图”；恢复连接后，由中央 Ledger 按版本和事件顺序接受一个动作，其余动作返回冲突。

**Consequences**：

- 保持单一权威 owner。
- 离线终端不能承诺取走最终成功。
- 需要明确冲突结果和用户修正路径。

**Verification**：构造两个终端对同一本书提交离线意图，验证最终只有一个有效持有人，另一个得到稳定冲突结果。

**Escape Hatch**：若离线冲突频率和人工处理成本不可接受，重新评估是否引入预分配令牌。

**Review Trigger**：离线登记成为主要入口，或冲突率超过项目明确设定的容忍值。

示例中的 `Accepted` 只是教学设定，不代表现实项目已审核或实现。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| 只记录结论 | 为什么没有选其他方案？ | 补 Context、Alternatives 和代价 |
| 把机制写成不变量 | 换一种机制还能保持核心性质吗？ | 分离稳定性质和当前实现 |
| 为所有小决定写 ADR | 它会长期约束多个工作吗？ | 局部选择留在 Task 或代码 |
| Deferred 没有触发条件 | 什么时候必须回来决定？ | 写依赖和重审条件 |
| 用分数伪装客观 | 每个分数由什么事实支持？ | 写具体理由和不确定性 |
| 决定没有验证 | 什么结果会证明判断错了？ | 补 Verification 与 Escape Hatch |

## 8. 与其他文档的输入、输出和更新关系

- 从 `01–05/07/08` 接收需要裁决的冲突和证据。
- 决定被接受后，分别传播到受影响的目标、边界、流程、契约、失败、验证和 Task。
- `09` 的 Human Review 决定 Proposed 是否变为 Accepted、Rejected 或 Deferred。
- “已接受”“已传播”“已实现”“已验证”分别追踪，不合并成一个完成状态。

## 9. 什么变化会触发本文更新

- 新证据改变候选方案的事实基础。
- Driver、约束或风险优先级改变。
- 达到 Review Trigger 或 Decision Horizon。
- 当前机制无法继续保持不变量。
- 决定被替代、撤销或明确延期。

不要改写旧 ADR 来伪装历史始终一致。用 Superseded 状态和新的 ADR 保留演进关系。
