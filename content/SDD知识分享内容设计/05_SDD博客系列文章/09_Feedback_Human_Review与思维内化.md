# 09 Feedback、Human Review 与思维内化

> SDD 系列第 9 篇｜上一篇：[08 Tasks](08_Tasks_从差距到可验证增量.md)｜下一篇：[回到总览](../SDD学习实战笔记.md)｜配套：[Human Review 模板](templates/Human_Review模板.md)与 [Learning Review Card](templates/Learning_Review_Card模板.md)

实现完成后，规格链仍会接收新证据。证据可能改变当前事实，也可能推翻已接受设计；人工评审要把变化送回负责该信息的位置，并把反复出现的判断盲点沉淀为下一次可复用的问题。

## 1. 本文回答的核心问题

`09` 回答两个相互连接的问题：

1. 实现与评审产生新证据时，系统设计应怎样回到正确层级持续修正？
2. 设计者怎样通过 Human Review（人工评审）和 AI 对照，把外部反馈逐步变成自己的判断能力？

`01–08` 维护项目信息，`09` 维护反馈方法。它不替代任何一份权威 Spec。

## 2. 系统反馈循环

### 2.1 主循环

```text
Goal
  → 01–07 Specification / Design
  → 08 Task
  → Implementation
  → Evaluation
  → Feedback / Design Delta
  → 回到信息实际发生变化的文档层级
  → 下一轮 Goal 或 Task
```

实现过程会检验设计假设。遇到冲突时，先判断哪类信息错了：

| 发现的问题 | 主要回写位置 | 常见下游检查 |
| --- | --- | --- |
| 为什么做、成功标准或范围错误 | `01` | `02–08` |
| 边界、职责或 owner 错误 | `02`，必要时 `06` | `03–08` |
| 流程、状态或生命周期错误 | `03` | `04/05/07/08` |
| 模块交互规则错误 | `04` | `05/07/08` |
| 失败分类或恢复责任错误 | `05` | `04/07/08` |
| 取舍理由或机制选择变化 | `06` | 实际受影响的 `01–08` |
| 证明方式不能验证承诺 | `07` | `08`，必要时上游 Spec |
| 实施顺序或范围错误 | `08` | 当前与后续 Task |
| 局部算法或私有结构问题 | Code / 当前 Task | 定向验证 |

从变化点向下做 impact analysis（影响分析），只更新实际受影响的位置。不要机械重写所有文档，也不要让代码差异成为未声明的新架构。

### 2.2 Design Delta 的适用边界

Design Delta（设计变化请求）适用于“已接受的 Spec 无法在当前证据下继续成立”，例如状态 owner 必须改变、公开契约无法兼容或恢复语义存在矛盾。

以下情况通常留在当前 Task：

- 私有函数命名。
- 不影响契约的局部算法选择。
- 现有范围内的测试修复。
- 可以由已接受设计唯一确定的实现接缝。

一条 Design Delta 至少说明：

- 冲突的 Spec 条目。
- 新发现的事实和证据基线。
- 为什么当前 Task 无法在原约束下完成。
- 最小变化选项及其影响。
- 当前工作应该继续、局部暂停还是完全阻塞。

### 2.3 五种状态必须分开

| 状态 | 含义 |
| --- | --- |
| `Draft` | 当前内容仍是提案，尚未被接受 |
| `Accepted` | 人已经接受目标或决定 |
| `Propagated` | 被接受的决定已写入受影响的权威文档 |
| `Implemented` | 代码或系统变化已完成 |
| `Verified` | 必需检查已在指定基线获得实际证据 |

这五项可能发生在不同时间。接受一个决定不表示已经传播或实现；测试计划存在也不表示验证已通过。

### 2.4 Task 完成后的同步

完成一个增量后：

1. 刷新 `08` 中受影响的 Current Facts。
2. 确认 Accepted Design Delta 已传播到正确的 `01–07`。
3. 记录实际验证、未验证限制和适用基线。
4. 将完成 Task 压缩成历史摘要。
5. 从新的 Current State 推导下一步；继续执行过期计划会扩大偏差。

## 3. Human Review 是两个循环的连接点

Human Review 同时承担事实核查、方案裁决、授权控制和学习反馈，批准 AI 输出只是其中一个动作。

### 3.1 五类检查点

| Review | 主要问题 | 推荐触发条件 |
| --- | --- | --- |
| Problem Review | Goal、Non-goal、SC 是否足以进入设计？ | 问题范围高影响或多方冲突 |
| Design Review | 边界、状态、契约、失败和 ADR 是否可接受？ | 难回退、跨模块或外部副作用 |
| Task Preflight Review | 基线、范围、接缝和验证门槛是否足以动手？ | 高风险实现前 |
| Design Delta Review | 新证据应被 Accept、Reject、Defer 还是继续调查？ | Spec 被实现证据挑战 |
| Completion Review | 结果、测试、边界和规范传播是否支持 Done？ | 项目规定或高风险任务完成时 |

低风险、容易回退的局部决定不必等待人工门禁。评审强度由风险决定。

### 3.2 三遍阅读法

第一遍看决定链：

- Objective
- Blocker
- Design Delta
- 推荐结论

第二遍 spot check（抽查）关键证据：

- 入口、状态 owner、公共契约、提交点和基线测试。
- 每个决定最关键的一到两个事实。
- 报告是否把假设写成当前事实。

第三遍独立比较方案：

- 是否有遗漏选项。
- 代价是否与 Driver 对齐。
- 可逆性和影响范围是否被低估。
- 验证是否真的能反驳错误方案。

Human 不需要全量复现调查，但必须验证决定链中最关键的事实。

### 3.3 Review 最少记录

- Objective 与适用基线。
- 已抽查的关键事实和证据。
- 每项问题的 Conflict、Options、Decision、Why、Trade-off 和 Reversibility。
- Accepted、Rejected、Deferred 与 Needs Evidence。
- GO、Conditional GO 或 NO-GO，以及允许继续的具体范围。
- 需要传播到哪些 `01–08` 文档。
- 传播和实现完成后怎样验证。

可复制结构见[Human Review 模板](templates/Human_Review模板.md)。

### 3.4 裁决语义

- **Accept**：决定进入已接受状态，随后按影响清单传播。
- **Reject**：当前方案不进入规范，并记录主要理由。
- **Explicitly Deferred**：明确延期，写出重审条件和受阻工作。
- **Needs Evidence**：信息不足，先执行限定范围的调查。
- **Conditional GO**：允许在列出的条件和范围内继续。
- **NO-GO**：依赖的关键事实或决定未解决，不得进入相应工作。

评审结论只影响依赖它的工作，避免用一个局部未决问题阻塞所有增量。

## 4. 个人思维反馈循环

### 4.1 Human-first / AI-second

在需要训练判断能力的设计任务中，推荐先由自己形成初步模型，再使用 AI 或同事作为对照：

```text
自己形成问题模型与设计草案
  → 记录假设、遗漏风险和预期结果
  → 请求外部批判、反例和候选方案
  → 独立核查关键事实
  → 比较两条推理链
  → 分类认知缺口
  → 提炼可复用原则或问题
  → 放回对应的 01–08 笔记与模板
  → 在下一次设计中主动调用
  → 用新结果继续校正
```

AI 在这个循环中提供审查压力和候选解释，不自动成为事实来源或决定者。

### 4.2 分类认知缺口

| 类别 | 典型表现 | 应回到的训练位置 |
| --- | --- | --- |
| 事实错误 | 没查现状，把旧文档当现实 | `01/08` 的事实与证据 |
| 覆盖遗漏 | 漏掉角色、状态、失败或质量属性 | 对应的 `01–07` 问题清单 |
| 层级错误 | 把目标、架构、契约和代码混在一起 | [总览笔记的文档地图](../SDD学习实战笔记.md) |
| 边界错误 | 没识别 owner、生命周期或依赖方向 | `02–04` |
| 取舍错误 | 只有推荐方案，没有代价和回退 | `06` |
| 任务错误 | 没从 Gap 推导最小增量 | `08` |
| 验证错误 | 把局部测试当整体完成 | `07/08` |
| 判断校准错误 | 对未知过度自信，或低风险问题审查过度 | 风险适配与 Review 门槛 |

分类用于找到应修改的问题框架，标签本身不产生修正动作。

### 4.3 使用 Learning Review Card

每次有价值的对照可以填写：

```text
Context:             当时要解决什么问题？
My Initial Model:    我原先怎样理解和判断？
External Feedback:   AI 或他人提出了什么不同意见？
Evidence Checked:    哪些事实经过独立核查？
Gap Category:        属于哪类认知缺口？
Accepted Learning:   最终接受、拒绝或延期了什么？
Principle:           能否提炼成跨场景原则？
Next Trigger:        下次遇到什么信号时主动调用？
Verification:        怎样观察自己是否已经掌握？
```

模板见[Learning Review Card](templates/Learning_Review_Card模板.md)。

### 4.4 决定什么进入长期知识库

一次性、强上下文相关的纠正留在私有复盘。只有满足以下条件的内容才升级为系列文章或模板中的通用规则：

- 已去除项目和个人可识别信息。
- 能抽象为跨场景问题或原则。
- 关键事实经过独立核查。
- 至少在一个后续情境中具有解释或预测价值。
- 能明确主要归属位置，避免重复定义。

AI 的每条建议都复制进知识库，会把工具输出堆成新的噪声。

## 5. 两个循环如何相互增强

- 系统循环提供真实问题、结果和失败证据，成为个人学习的样本。
- 个人循环把反复出现的盲点压缩成 Ownership、Lifecycle、State、Contract、Failure、Trade-off 和 Evidence 等可复用模式。
- 内化后的问题框架会在下一轮 `01–08` 设计中更早出现。
- Human Review 决定哪些反馈可信、哪些设计被接受、哪些经验值得长期保存。
- 新实践继续检验这些原则，避免把一次成功经验误写成永恒规则。

## 6. 独立虚构示例

> 教学推演：以下“校园讲座候补名单”完全虚构，只用于说明系统反馈和个人学习；没有真实实现或验证结果。

### 6.1 系统反馈

初始设计假设：取消报名后，系统立即把名额分配给候补第一名，并发送外部通知。

实现调查发现：外部通知服务只返回超时，没有幂等键，也没有结果查询接口。因此“超时后自动重发”可能造成重复通知。

正确处理链：

1. 在 `08` 记录当前外部契约证据与阻塞。
2. 回到 `03`，增加“通知结果未知”状态。
3. 检查 `04` 的超时语义、`05` 的恢复 owner、`07` 的未知状态测试。
4. 在 `06` 比较人工确认、替换供应方或接受重复风险等选项。
5. 经 Design Delta Review 接受决定后，再传播到 Task。

实现者不应在适配器中私自增加无限重试。

### 6.2 个人学习

设计者原先把“HTTP 超时”理解为“通知未发送”。外部反馈指出远端可能已提交。

核查外部契约后，认知缺口被归为“失败语义 + 判断校准错误”。适合长期保留的问题是：

> 当外部动作有副作用且响应丢失时，是否存在接收端幂等键或结果查询能力？

这个问题适合进入 `04/05` 的长期检查清单；具体供应方超时细节只留在项目内部复盘。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| AI 建议直接进入规范 | 关键事实独立核查了吗？ | 先验证、再 Human Review |
| 实现冲突全部叫 Design Delta | 已接受 Spec 真错了吗？ | 区分局部实现问题 |
| 一个 Delta 重写所有文档 | 哪些下游承诺真的受影响？ | 做定向影响分析 |
| 接受决定就标记完成 | 传播、实现和验证分别完成了吗？ | 五种状态分开追踪 |
| 每个小改动都等人工批准 | 影响大或难回退吗？ | 按风险设置门槛 |
| 复盘只记录“以后注意” | 下次出现什么信号？怎样验证改进？ | 写 Trigger 和 Verification |

## 8. 更新和使用边界

更新本篇的触发条件包括：

- 评审类型、门槛或裁决语义改变。
- Design Delta 的分类与传播规则改变。
- 学习缺口分类或知识升级标准改变。
- 实践证据证明现有反馈方法无法支持判断。

具体项目的评审结论、个人原始 Learning Review 和可识别实施记录不进入本篇。
