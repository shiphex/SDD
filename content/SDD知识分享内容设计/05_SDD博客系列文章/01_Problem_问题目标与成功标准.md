# 01 Problem：问题、目标与成功标准

> SDD 系列第 1 篇｜上一篇：[总览：小白如何用 SDD 与 AI 开发软件](../04_小白如何用SDD与AI开发软件_博客.md)｜下一篇：[02 Architecture](02_Architecture_边界职责与所有权.md)｜配套：[01 Problem 模板](templates/01-problem模板.md)

很多开发任务从“要做什么功能”开始，却没有先说明问题是否真实、结果怎样观察、哪些相邻需求不在本次范围。本文从这几个最早也最容易被跳过的判断开始。

## 1. 本文回答的核心问题

`01` 回答：为什么要做这次变化，当前问题是什么，哪些内容不在范围内，以及出现什么可观察结果才算成功。

它不回答模块怎样划分、接口叫什么或代码放在哪个文件。这些属于后续设计或实现。

## 2. 为什么需要这份文档

没有明确的问题定义，团队很容易把“看起来合理的方案”误当成目标。例如“新增一个缓存层”描述的是候选机制，不说明要改善哪种用户体验、当前瓶颈是否存在，也无法判断何时停止。

`01` 提供整个设计链的起点：

- `Goal` 约束要得到的结果。
- `Non-goal` 防止相邻需求被顺手带入。
- `Architecture Drivers`（架构驱动因素）说明哪些质量和约束会显著影响设计。
- `Success Criteria`（成功标准，简称 SC）把目标转成可观察的验收条件。

## 3. 写作前需要哪些输入

至少准备：

- 当前请求和交付类型：调查、设计、实施还是内容制作。
- 受影响角色和他们当前遇到的问题。
- 与问题直接相关的当前行为或证据。
- 已知的业务、合规、时间和兼容约束。
- 明确排除的相邻目标。

如果现状尚未核实，可以把它标为“待核实假设”，不要把它写进当前事实。

## 4. 设计时应依次思考哪些问题

### 4.1 先定义问题，不先选机制

用三句话建立问题模型：

1. 谁在什么情境下遇到什么可观察问题？
2. 这个问题造成什么实际影响？
3. 为什么值得现在处理？

“系统缺少消息队列”已经预选了方案，无法完整描述问题。可改为：“批量导入时，请求需要等待全部条目处理完成；任一条目超时会让调用方失去整体进度。”

### 4.2 区分设计基线与滚动事实

`01` 可以记录解释问题所需的设计基线，例如“当前用户必须等待同步处理返回”。这是一段相对稳定的背景。

实施期间不断变化的文件、测试和分支事实放在[08 Tasks](08_Tasks_从差距到可验证增量.md)的 `Current Facts` 中。两者边界是：

- `01` 只保留理解问题和验收目标必需的现状。
- `08` 维护当前增量可以开始和结束的最新证据。

### 4.3 写结果式 Goal

Goal 描述变化完成后可以观察到的能力或性质，不提前指定私有实现。

```text
不推荐：创建 QueueManager 类并修改 importer.py。
推荐：批量导入请求可以立即获得任务标识，并查询每个条目的处理结果。
```

项目同时具有学习或流程目的时，可以分开记录：

- **产品目标**：系统或用户获得什么能力。
- **学习目标**：本次实践希望掌握什么判断方法。
- **流程目标**：准备沉淀什么可复用检查项。

只有产品目标通常参与功能完成判定。学习和流程目标应有各自证据，不能让它们扩大产品范围。

### 4.4 用 Non-goal 形成停止线

Non-goal 应选择最容易被“顺手做掉”的相邻内容，无需罗列整个系统里所有无关功能。

好的 Non-goal 可以直接下沉为 `08` 的 `Must not`，例如：

- 本阶段不提供任务优先级。
- 本阶段不替换既有身份认证方式。
- 本阶段不承诺跨数据中心恢复。

Non-goal 只限定当前范围。如果某项内容只是延期，应记录触发重审的条件。

### 4.5 识别 Architecture Drivers

架构驱动因素是会显著改变方案的约束或质量目标，例如：

- 必须兼容既有调用方。
- 外部服务可能超时，且调用具有不可逆副作用。
- 进程重启后仍需恢复关键状态。
- 预期并发、响应时间或数据保留要求。

不要写无法验证的形容词，如“高性能”“高可用”。改写为具体情境和可测响应，详细方法见[07 Test Plan](07_Test_Plan_验证设计与完成条件.md)。

### 4.6 把成功标准写成场景

推荐使用 Given / When / Then：

```text
SC-01
Given：一个批次包含三个格式有效的条目
When：调用方提交批次
Then：调用方立即获得批次标识，并能查询三个条目的独立状态
```

每条 SC 应满足：

- 观察者明确。
- 触发条件明确。
- 结果可验证。
- 不夹带未经裁决的实现细节。
- 能在 `07` 找到对应的证明方式。

### 4.7 定义停止条件

Problem 设计可以在以下信息足以支持下一步时停止：

- Goal、Non-goal 和 SC 能判断结果是否完成。
- 影响架构的主要驱动因素已明确。
- 未知项被标出，并有调查入口或不阻塞理由。

不需要在 `01` 解决所有设计问题。

## 5. 最小内容与高风险扩展内容

### 5.1 最小内容

- Background / Problem
- Current baseline
- Goal
- Non-goal
- Success Criteria

### 5.2 高风险扩展

在高影响、难回退或受监管的变化中补充：

- 利益相关者与受影响角色。
- Architecture Drivers 及优先级。
- 假设、未知项和调查责任。
- 明确的风险容忍度和停止条件。
- 需求冲突及 Problem Review 结论。

## 6. 独立虚构示例

> 教学推演：以下“社区工具借用站”完全虚构，只用于说明 Problem 写法，不代表存在对应系统或验证结果。

### 6.1 Problem

值班员目前用一张当天表格登记工具借出。闭站前若借用人尚未归还，下一班值班员只能逐行翻查，容易遗漏仍在借出的物品。

### 6.2 Goal

- 值班员可以查看当前仍未归还的借用记录。
- 交接班后，未归还记录仍保持可查询。

### 6.3 Non-goal

- 不做会员收费。
- 不做工具损坏定责。
- 不发送短信或邮件提醒。

### 6.4 Architecture Drivers

- 交接班过程中不能丢失未归还状态。
- 既有当日登记方式需要在过渡期继续可用。

### 6.5 Success Criteria

```text
SC-01
Given：记录 A 已借出且尚未归还
When：新值班员进入交接后的工作台
Then：记录 A 仍显示为“借出中”

SC-02
Given：记录 A 处于“借出中”
When：值班员登记归还
Then：记录 A 不再出现在未归还列表，并保留归还时间
```

示例只形成待设计目标。存储方式、状态 owner 和并发冲突仍需在 `02–06` 中裁决。

## 7. 常见错误与诊断方式

| 错误 | 诊断问题 | 修正方向 |
| --- | --- | --- |
| Goal 写成类名或文件改动 | 换一种实现还能满足目标吗？ | 改成可观察结果 |
| 背景全是旧文档结论 | 当前版本有证据吗？ | 标为假设或补充核实 |
| Non-goal 过长 | 哪些相邻内容最可能被顺手实现？ | 只保留有防扩张价值的项 |
| SC 写成“测试通过” | 测试要证明什么行为？ | 先写行为，再在 `07` 设计证据 |
| 把学习目标当产品完成条件 | 用户能力是否因此变化？ | 分开目标和证据 |
| 一直补充背景无法停止 | 已能判断做成与没做成的差异吗？ | 达到停止条件后进入设计 |

## 8. 与其他文档的输入、输出和更新关系

- 输出给 `02–06`：Goal、Non-goal、Drivers 和关键未知项。
- 输出给 `07`：每条 SC 及其观察者、条件和预期结果。
- 输出给 `08`：Task Goal 的上位目标与 Must not 的来源。
- 从 `08/09` 接收：实现或评审证明问题定义失真时形成的 Design Delta。

Goal 变化会影响整条规格链。需要检查边界、流程、契约、失败、决定、测试和当前 Task 是否仍然成立。

## 9. 什么变化会触发本文更新

- 目标用户或问题情境改变。
- Goal、Non-goal 或成功标准被接受性地调整。
- 关键约束、兼容承诺或风险容忍度改变。
- 新证据证明原设计基线不足以解释问题。

任务完成后的普通文件变化不会自动触发 `01` 更新。
