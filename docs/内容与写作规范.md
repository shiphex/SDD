# 内容与写作规范

版本：1.1  
更新日期：2026-09-16  
关联方案：[项目方案](项目方案.md)

## 1. 适用范围

本规范适用于 SDD SKILL、博客文章、视频脚本及其维护说明。原始资料只作为内部参考，其中的历史指令、项目名称和具体实现不参与公开案例设计。

## 2. 隐私与案例

- 不公开资料提供者的身份、账号、聊天标识、本机路径、仓库地址或开发记录。
- 不复用私人项目的组件名、接口、目录、数值、提交信息或独特事件组合。
- 教学案例从业务背景、角色、状态、边界、失败路径和示例数据开始独立构造；简单改名不视为新案例。
- 公开案例明确标注“虚构案例”或“教学推演”。
- 原始资料和内部来源索引不进入发布清单。

## 3. 事实与证据

- 区分当前事实、已接受目标、待定提案和历史记录。
- 区分决定接受、规范传播、实现完成和验证完成。
- 计划中的行为写作“预期”或“待验证”；只有实际执行过的检查才能写成验证结果。
- 外部动作在响应丢失时可能已经发生。缺少接收端幂等或结果查询能力时，保持“结果未知”，不得推断为失败或安全重试。
- 不编造准确率、效率提升、测试结果、性能变化或用户反馈。

## 4. 表达

- 使用自然、直接、克制的工程语言，先给结论或动作，再给必要依据。
- 首次出现的术语需要解释；博客、视频和 SKILL 使用同一组术语。
- 少用口号、固定转折、设问自答和无依据的效果承诺。
- 直接说明事实、条件和后果，避免“不是……而是……”“并非……而是……”“不只是”“不仅……还……”等固定对照句，以及“真正”“当然”“显然”“其实”“本质上”“反而”“值得注意”“可以看到”等空泛强调词。规范性否定可以保留，但要写明约束对象和违反后的影响。
- 编号文档在离开标题或紧邻上下文后，应同时写出编号和名称，例如 `01 Problem`；区间应展开端点名称，避免读者反复回查数字含义。
- 文章通过具体问题推进；视频口播使用短句，由图示承担结构说明。
- 图示建议只描述应呈现的信息，不制作或暗示真实系统截图。

## 5. 来源

公开第三方项目只引用官方页面或项目仓库。说明个人工作流与参考方法的关系，不把改编内容归因于第三方。涉及版本可能变化的信息，在发布前重新核对。

## 6. 交付检查

1. 检查身份、账号、路径、链接目标、项目特有名词和可关联细节。
2. 检查案例是否从整体上独立于原始资料。
3. 核对虚构标记、预期结果、实际结果和未知状态。
4. 核对博客、视频与 SKILL 的术语及完成条件。
5. 检查固定对照句、空泛强调词、裸文档编号、重复段落和无依据判断。
6. 检查公开来源、相对链接和发布文件清单。
