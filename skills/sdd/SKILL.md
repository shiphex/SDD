# SDD

先确认当前请求是调查、设计、计划、实施、评审、收尾还是内容制作。用户只要求分析或评审时保持只读；只有当前请求授权实施时才修改代码或运行会改变外部状态的操作。

读取[七步工作流](references/workflow.md)。需要创建或维护 Spec、决定、任务或完成记录时，再读取[产物与输出](references/artifacts.md)。

## 输入

优先使用用户和目标项目已经提供的信息：

- 要解决的问题、目标、非目标和成功标准。
- 当前代码、规范、任务、决定和可复核证据。
- 本次授权范围、禁止事项及项目约定。
- 已知风险、兼容要求和未决问题。

缺失信息能从代码或文档核实时先调查。只有会实质改变目标、公开契约或实施方向的偏好需要用户决定。

## 执行边界

- 区分当前事实、已接受目标、待定提案和历史记录。
- 从现状与目标的差距推导工作，不从预想的文件列表反推需求。
- 文档深度随影响、可逆性和不确定性调整。
- 局部实现选择在授权范围内处理；改变公开契约、状态责任、持久化或重要失败保证时记录决定。
- 接受、传播、实现和验证分别记录。未传播的决定不能作为已完成实现的替代品。
- 外部结果未知时保持未知。没有接收端幂等或状态查询能力，不承诺恰好一次。
- 内容制作只交付文字、伪代码和图示说明，不为证明观点创建项目或评估目录。

## 输出顺序

先说明当前结论、可推进范围和阻塞项，再给必要证据及下一步。实施任务完成时列出实际变化、已运行检查、覆盖限制和剩余工作。

只有[七步工作流](references/workflow.md)中的完成条件全部满足时，才报告任务完成。
